# RPGCore

Paper 서버용 RPG 플러그인. 스탯/레벨, 직업, 순위표, 파티, 플레이어 간 거래,
업적과 칭호, 수집 도감, 1:1 대결, **골드 경매장**, **수요·공급으로 값이 움직이는 시장**,
**예금·대출·신용등급이 있는 은행**, **물가를 보고 금리를 정하는 중앙은행**,
**공장을 돌리고 주식을 발행하는 기업**, **자본이 무너지면 파산하는 부실 기업**,
**공급이 모자라면 국가가 세우는 공기업**, **시세로 값을 치르면 스스로 올라가는 청사진**,
소지 무게,
장비 내구도 페널티, 연쇄 벌목, 모루 커스텀 강화, 근접 채팅, **Discord 알림**을
한 덩어리로 제공합니다.
이름표와 플레이어 목록, 아이템 툴팁에도 RPG 정보가 함께 표시됩니다.

**`/menu` 하나면 됩니다.** 기능마다 명령어를 외울 필요 없이 상자 창 하나에서
모든 화면으로 이동합니다.

**기본으로 들어 있는 콘텐츠** — 직업 19종(3단계 + 경제 직업 4종), 업적 50개, 칭호 54개,
도감 20분류 363종, 모루 강화 16종, **시장 품목 104종(6분류)**,
**공장 25종**, **기초 기업 8곳**.
전부 설정 파일이라 코드 수정 없이 늘릴 수 있습니다.

- **jar 하나가 전부입니다.** 데이터팩도, 다른 플러그인도, 외부 라이브러리도 필요 없습니다.
- **전부 서버 사이드 로직**이라 자바와 베드락(Geyser) 플레이어가 **완전히 동일하게** 동작합니다.
- 설정은 `config.yml` 한 파일. 대부분 `/rpgcore reload` 로 재시작 없이 반영됩니다.

## 설치

**요구사항: Paper 26.2 이상, Java 25** (Paper 26.2 자체가 Java 25를 요구합니다.)

1. `plugin/` 에서 빌드 → `plugin/target/rpgcore-plugin-2.9.0.jar`
   ```
   cd plugin && JAVA_HOME=/path/to/jdk-25 mvn package
   ```
2. jar 를 서버 `plugins/` 에 넣고 재시작.
3. 끝. `plugins/RPGCorePlugin/` 에 설정 파일이 자동 생성됩니다.
   - `settings.yml` — 최대 레벨, 경험치 곡선, 인챈트 한계, 기능 on/off (**주로 여기만**)
   - `jobs.yml` — 직업 정의
   - `economy.yml` — 시장 품목표, 임금과 초기 공급, 금리, 지급준비율, 물가목표
   - `corporations.yml` — 공장 종류, 주식·배당·인수 규칙, 기초 기업
   - `config.yml` — 아이템 분류, 모루 조합법 등 세부 설정

기동 로그에 아래처럼 뜨면 정상입니다.


숫자가 위와 다르면 그만큼 건너뛴 것입니다. **이 서버 버전에 없는 아이템이나 태그는
경고 한 줄을 남기고 넘어가므로**, 기동 로그에 `WARN` 이 없다면 설정이 전부 읽힌 것입니다.

(음성은 자바 클라이언트 모드가 필요합니다. 베드락은 근접 **텍스트** 채팅으로 동작합니다.)

## 기능

### `/menu` — 전부 여기서
상자 창 하나에서 스탯 · 직업 · 칭호 · 도감 · 업적 · 순위표 · 파티 · **시장 · 은행 · 경제 지표** ·
**기업 · 거래소 · 청사진** · 경매장 · 우편함으로 바로 갑니다. 화면끼리 서로 오갈 수 있으므로 명령어를 몰라도 기능을 전부 찾을 수 있습니다.

가운데 위에 레벨 · XP · 무게가, 아래에 골드 잔액과 우편함이 붙습니다. 우편함에 받을 것이
있으면 아이콘이 엔더 상자로 바뀌므로 따로 알려 주지 않아도 눈에 띕니다.

`settings.yml` 에서 끈 기능은 **자리를 비우지 않고 회색 칸으로 남습니다.** 서버마다 버튼
위치가 달라지면 익힌 배치가 소용없어지기 때문입니다.

### 기업
`/menu` → 기업, 또는 `/company`. **시장의 공급 쪽**입니다. 공장이 매 경제일마다 물건을
만들어 창고에 쌓고, 정책에 따라 시장에 내다 팔아 매출을 냅니다. 길드를 대체합니다.

```
공장이 만든다 → 창고에 쌓인다 → 시장에 판다 → 매출
   → 유지비·원료비·임금을 빼면 이익 → 배당으로 주주에게
```

- **창업** `/company create <이름>` — 자본금 25,000골드(그중 5,000은 등록세로 국고에).
  발행주식 10,000주가 전부 창업자 몫이 됩니다.
- **공장 25종**. 채취(채석장·광산·농장·어장…)와 가공(제련소·제빵소·유리공장…)이 있고,
  **가공 공장은 원료가 필요합니다.** 창고에서 먼저 쓰고 모자라면 시장에서 사 옵니다.
  그래서 철광산은 남의 제련소가 사 주기 때문에 값어치가 있고, 원료가 없는 제련소는
  물건을 만들어 내지 못하고 조용히 멈춥니다.
- **증설** 최대 5단계. 단계마다 생산량 x1.6, 건설비 x1.8, 유지비 x1.45.
- **직원**. 채용하면 매 경제일마다 일당이 나갑니다(기본 300, 대표 2배). 현금이 없으면
  체불되고, 3일 연속 체불되면 직원이 떠납니다. 회사원이 되는 것만으로 수입이 생깁니다.
- **납품** `/company supply` — 직접 캔 물건을 회사 창고에 넘기고 시장 매도가를 받습니다.
- **정책** 출고 비율(창고의 몇 %를 매일 팔지), 배당 비율, 원료 자동 조달 on/off.
- **법인세** 그날 이익의 15%가 국고로 들어갑니다. 적자인 날은 내지 않습니다.
- **회사 명의 대출** `/company loan <금액> [일수]` — 개인 한도와 별개로, **자산의 60%까지**
  빌립니다. 자산은 현금 + 창고 + 설비이고, 이자는 매 경제일 비용으로 잡힙니다.
  갚는 것은 `/company repay`.

기본 공장 수지는 **지금 시세로 계산해서** 잡아 두었습니다 — 어느 공장이든 건설비를
대략 15경제일에 회수합니다. 시세가 움직이면 그 수지도 같이 움직입니다.

#### 부실과 파산

회사의 **자본 = 자산(현금 + 창고 + 설비) − 부채(은행 대출 잔액)** 입니다. 이 숫자가
무너지는 과정을 단계로 나눠 뒀습니다. 갑자기 사라지지 않고, 경고가 먼저 옵니다.

```
부채비율 400% 초과 또는 자본 마이너스  →  관리종목 지정 (전체 공시, 주가에 −25% 벌점)
자본이 마이너스인 채로 3경제일          →  파산
파산 → 자산을 팔아 은행 빚부터 갚고, 남은 것만 주주에게.
       모자란 빚은 은행이 손실 처리합니다.
```

- **빚이 있는 회사에서는 자본을 넘겨 뺄 수 없습니다.** `/company withdraw` 는 자본까지만
  허용합니다 — 빌린 돈을 대표가 들고 나가고 빚만 남기는 것은 구멍이 아니라 사기입니다.
- 자본이 처음 마이너스가 된 날 대표에게 **"3일 안에 회복하지 못하면 파산한다"** 고
  알립니다. 증자(`/company issue`)·설비 매각·상환 중 하나를 하면 됩니다.
- 회복하면 관리종목에서 **해제**되고, 그것도 공시됩니다.
- 은행이 떼인 돈은 은행 자본에서 빠집니다. 그래서 큰 회사 하나가 무너지면
  **은행 건전성 지표가 같이 나빠지고**, 자본이 바닥나면 중앙은행이 발권해서 메웁니다 —
  구제금융도 통화량이라 물가에 닿습니다.

### 거래소 (기업 투자)
`/menu` → 거래소, 또는 `/stocks`. 남의 회사 지분을 사서 배당을 받고, 모아서 인수합니다.

**서버를 열면 기초 기업 8곳이 이미 돌아가고 있습니다** — 대한광업, 한빛제철, 푸른농장,
백두목재, 동해수산, 금성정련, 남해건자재, 흑암보석. 첫날부터 생산하고 배당을 냅니다.
지분의 70%는 **공모 물량**(일반 투자자가 이미 보유)이고 30%는 **자사주**입니다.

- **투자** = 자사주를 사는 것입니다. 낸 돈은 그대로 **회사 현금이 되어 다음 공장이 됩니다.**
  플레이어끼리의 내기가 아니라 실제 자금 조달입니다. 호가창이 필요 없는 이유이기도 합니다.
- **매도**는 회사가 되사 줍니다(자사주 매입). 회사 현금에서 나가고, 하루 매입 한도는
  현금의 25%입니다. **현금이 없는 회사의 주식은 팔고 싶어도 못 팝니다** — 작은 지분이
  실제로 갖는 비유동성이고, 화면에 그렇게 적혀 있습니다.
- **주가** = 기업가치 / 유통주식수(발행 − 자사주).
  기업가치는 **장부가**(현금 + 창고 + 설비)와 **수익가치**(연이익 x PER 8)의 가중평균입니다.
  자사주를 제값에 팔면 회사 현금이 그만큼 늘어 주당 가치가 그대로입니다 — 희석이
  값어치를 훔쳐가지 않습니다.
- **주문은 자기가 민 값으로 체결됩니다.** 큰 매수는 주가를 밀어 올리는데, 그 주문을
  밀기 전 값으로 체결해 주면 사자마자 되팔아 차익이 납니다. 밀기 전과 후의 중간값으로
  체결하므로 **왕복 매매는 스프레드와 거래세만큼 손해**입니다. 한 주문이 밀 수 있는
  폭에는 상한(기본 100%)이 있습니다 — 없으면 큰 매도가 주가를 0 밑으로 끌어내립니다.
- **자사주 매입으로 유통주식을 전부 거둬들일 수는 없습니다**(발행량의 10%가 하한).
  유통이 0이 되면 주당 가치가 정의되지 않고, 그 상태에서 한 주를 사는 사람이 회사 전체를
  가져가게 됩니다.
- **배당** 이익의 40%(기본)를 **지분 비율대로** 나눠 줍니다. 공모 물량 몫은 국고로.
  주당 정액이 아니라 비율인 이유는, 1만 주짜리 회사의 하루 이익으로는 주당 배당이
  1골드에 못 미쳐서 정액 방식이면 **아무도 못 받기** 때문입니다.
- **인수** `/company acquire <회사> [프리미엄%]` — 아직 갖지 못한 **유통 주식 전부**를
  시가+프리미엄에 사들입니다. 기초 기업은 즉시 체결되고, 사람이 운영하는 회사는 대표가
  수락해야 합니다(이미 과반이면 수락 없이 진행).
- **합병** `/company absorb <회사>` — 100% 확보한 자회사를 흡수합니다. 현금·창고·공장·직원이
  모두 모회사로 옮겨옵니다.
- 회사가 다른 회사의 주식을 가질 수 있습니다. 주주 명부의 키가 UUID이고 회사 ID도
  UUID라서, 모회사가 자회사 배당을 받는 데 특별한 처리가 없습니다.

### 공기업 (공급이 모자라면 국가가 세웁니다)

시장에 어떤 물건이 계속 모자란데 아무도 그걸 만들지 않으면 — 만들 사람은 공장을 지을
돈이 없고, 돈이 있는 사람은 다른 걸 만드는 게 더 남기 때문에 — 그 품목은 영원히 비쌉니다.
그래서 **국가가 나섭니다.**

```
어떤 품목의 장 마감 재고가 기준재고의 40% 미만  →  '부족' 하루로 셈
그게 3경제일 연속                                →  그 품목을 만드는 회사를 국고 25만으로 설립
재고가 기준의 130%를 넘은 상태가 5경제일        →  민영화, 지분이 거래소에 풀림
```

- **장 마감 재고로 셉니다.** 시장은 매 경제일 기준재고 쪽으로 25%씩 회복하는데(세상에서
  계속 캐고 있다는 뜻), 회복한 뒤의 재고를 보면 그날 실제로 바닥났던 품목이 전부
  정상으로 보입니다. 재는 것은 **하루 장사가 끝났을 때 선반에 남아 있던 양**입니다.
- 설립 자금은 **국고에서** 나갑니다(모자라면 중앙은행이 발권 — 재정적자가 물가로 갑니다).
  카탈로그에 그 품목을 만드는 공장이 없으면 세우지 않습니다. 국가도 만드는 법을 모르는
  물건은 못 만듭니다.
- **공기업 지분은 살 수도 인수할 수도 없습니다.** 전량 국가 보유이고, 거래소에서는
  "살 수 있는 물량 없음 (전량 국가 보유)" 으로 뜹니다.
- 적자가 나도 **파산하지 않습니다** — 국고에서 메웁니다. 일부러 세운 회사이고, 국가는
  그걸 감당할 수 있습니다. 그 대신 그 돈도 통화량입니다.
- **민영화**되면 국가 지분이 거래소에 풀리고, 판 대금은 **국고로 돌아갑니다**. 그때부터는
  보통 회사와 똑같이 살고 죽습니다.
- 한 번에 하나씩, 최대 8곳까지. 전부 `corporations.yml` 의 `state-enterprise:` 에 있습니다.

### 청사진 (대규모 건축)
`/menu` → 청사진, 또는 `/blueprint`. **구역을 떠서 저장하고, 자재값을 시장 시세로 치르면
그 자리에 자동으로 올라갑니다.**

1. `/blueprint wand` 로 설계 지팡이를 받아 **좌클릭 1번 모서리, 우클릭 2번 모서리**
   (또는 서 있는 자리로 `/blueprint pos1` · `pos2`)
2. `/blueprint save <이름>` — 블록 종류와 방향까지 그대로 뜹니다(계단 방향, 문 위아래 포함)
3. `/blueprint cost <이름>` — **자재 목록과 값**을 봅니다
4. `/blueprint build <이름>` — 서 있는 자리에 착공. 뒤에 `company` 를 붙이면 회사 자금으로

- **값은 고정표가 아니라 그날 시장에서 뽑습니다.** 자재 한 종류를 많이 쓸수록 곡선을 따라
  비싸지고, 실제로 시장 재고를 사 갑니다. 그래서 큰 공사는 자재값을 끌어올리고, 그만큼
  누군가의 공장이 값어치를 합니다. 재고가 모자라면 그만큼은 **수입 할증**이 붙습니다.
- **공사는 시간이 걸립니다.** 초당 40블록씩 아래층부터 쌓입니다(5만 블록이면 약 21분).
  물리 효과를 끄고 놓으므로 공사 중에 모래가 무너지거나 물이 흐르지 않습니다.
- 서버를 재시작해도 **진행 상황이 그대로 이어집니다**(남은 위치를 정수 하나로 기억합니다).
- `/blueprint rush` 로 급행비를 내고 즉시 완공, `/blueprint cancel` 로 중단(자재는 환불되지 않습니다).
- **공사 구역 안에 있으면 밖으로 밀려납니다.** 안 그러면 자기가 주문한 건물에 파묻힙니다
  (검증 중에 실제로 그렇게 죽었습니다).
- 한 변 128블록, 총 5만 블록까지. 저장은 팔레트 + 런렝스 압축이라 벽 한 면이 한 줄입니다.


### 경매장
`/menu` → 경매장, 또는 `/auction`. 골드를 실제로 쓸 곳이자, 서버에 쌓인 골드가 빠져나가는
곳입니다.

- `/auction sell <시작가> [즉시구매가]` — **손에 든 물건**을 올립니다. 즉시구매가를 적지
  않으면 순수 입찰 경매가 됩니다.
- 좌클릭으로 입찰, 우클릭으로 즉시구매. 자기 물건은 우클릭으로 내립니다.
- 입찰하는 순간 골드를 **실제로 걷어 갑니다.** 그래서 밀려난 사람은 그 자리에서 전액을
  돌려받고, 낼 수 없는 입찰이라는 것이 존재하지 않습니다.
- 마감 직전 입찰이 들어오면 종료가 미뤄집니다(`anti-snipe-seconds`). 없으면 "마지막 순간에
  찔러 넣기"가 최선의 전략이 되어 값이 아니라 핑으로 이기는 경매가 됩니다.
- **입찰이 하나라도 들어오면 판매자는 물건을 내릴 수 없습니다.** 그렇지 않으면 모든 입찰이
  판매자 기분에 거는 도박이 됩니다.

수수료가 두 가지입니다. 등록 수수료는 올릴 때 받고 유찰돼도 돌려주지 않으며(빈 물건 도배
방지), 판매 수수료는 팔렸을 때 낙찰가에서 뗍니다. 둘 다 `config.yml` 의 `auction:` 에 있고,
0 으로 두면 골드가 서버에 쌓이기만 합니다.

### 우편함
낙찰된 물건, 판매 대금, 밀려난 입찰금, 유찰된 물건, 무승부로 끝난 대결의 판돈 — **받을
사람이 접속 중이 아닐 때 생기는 것**은 전부 우편함(`mailbox.yml`)에 들어가고 다음 접속에
자동으로 전달됩니다. `/menu` 의 우편함 칸이나 `/auction collect` 로도 받습니다.

UUID 로 보관하므로 닉네임을 바꿔도 따라옵니다. 인벤토리가 가득 차면 **바닥에 버리지 않고**
그대로 두고 알려 줍니다 — 용암 위에 서 있는 사람 발밑에 떨구는 것보다 낫습니다.

### 시장
`/menu` → 시장, 또는 `/market`. **값이 정해져 있지 않은 상점**입니다. 104종을 6분류로
취급하고, 값은 서버가 무엇을 얼마나 캐고 얼마나 사 갔는지에 따라 매일 움직입니다.

**품목표에는 가격이 없습니다.** `economy.yml` 에 적는 것은 "한 사람이 한 시간에 몇 개나
얻는가"(`per-hour`) 하나뿐이고, 거기서 두 가지가 계산되어 나옵니다.

```
기준가  = (시간당 임금 / 시간당 채굴량) x 수요계수
기준재고 = 시간당 채굴량 x 초기공급시간 x 기준인원      <- 초기 공급량
```

앞은 노동가치설입니다. 한 시간을 캐면 무엇을 캐든 대체로 같은 값어치를 번다는 뜻이라,
시간당 18개 나오는 다이아는 시간당 420개 나오는 석탄의 23배가 **자동으로** 됩니다.
뒤가 요청하신 "채굴 속도에 따른 초기 공급"입니다. 흔한 것은 처음부터 산더미로 깔려 있고
귀한 것은 몇 개 없습니다. 서버 규모가 다르면 `reference-players` 하나만 바꾸면 모든
품목의 공급이 같은 비율로 따라갑니다.

기본값(시급 1200, 24시간 x 10명)으로 실제로 이렇게 잡힙니다.

| 품목 | 시간당 | 기준가 | 초기 공급 |
|---|---|---|---|
| cobblestone | 3,000 | 0.24 | 720,000 |
| coal | 420 | 3.14 | 100,800 |
| iron_ingot | 240 | 7.00 | 57,600 |
| diamond | 18 | 120 | 4,320 |
| netherite_ingot | 0.6 | 5,000 | 144 |
| nether_star | 0.4 | 9,000 | 96 |

**값은 재고로 정해집니다.**

```
가격 = 기준가 x (기준재고 / 현재재고) ^ (1 / 수요탄력성) x 심리 x 물가수준
```

탄력성이 작을수록 필수품이고, 필수품일수록 값이 **더 크게** 요동칩니다. 빵값이 두 배가
되어도 사람은 빵을 먹지만 다이아 값이 두 배면 그냥 안 사기 때문입니다. 밀·빵은 0.5~0.6,
다이아는 1.3, 흙은 2.0 으로 들어 있습니다.

- 좌클릭 1개 구매 / Shift+좌클릭 한 묶음 / 우클릭 1개 판매 / Shift+우클릭 전량 판매
- **한 번에 많이 사면 점점 비싸집니다.** 주문을 1개씩 곡선을 따라 계산하므로, 창고를 통째로
  사면 사는 도중에 값이 오릅니다. 실제 호가창과 같은 방식이고, 이게 없으면 첫 개 값으로
  창고를 비우는 거래가 성립합니다.
- **살 때와 팔 때 값이 다릅니다**(스프레드 6%) + 거래세 5%. 그래서 시장에서 사서 시장에
  되파는 무한 반복은 반드시 손해입니다.
- 시장에는 **지갑이 있습니다**(기본 300만). 팔면 그 돈이 빠져나가고, 바닥나면 매입이
  멈춥니다. 그때는 중앙은행이 발권해서 채우고 — 그건 공짜가 아니라 물가로 돌아옵니다.
- **창고에도 한계가 있습니다.** 기준재고의 20배까지 차면 더 사지 않습니다(공급 과잉).
- 이름을 바꾸거나 인챈트한 물건은 **취급하지 않습니다.** 잘못 친 숫자 하나로 멘딩 곡괭이를
  잡템 값에 넘기는 일이 없어야 하기 때문입니다. (무게 툴팁은 플러그인이 붙인 것이므로
  예외로 봅니다.)
- 블록을 캐면 그 품목의 공급이 그만큼 늘어납니다. 한 블록은 창고에 티도 안 나지만,
  서버 전체가 저녁 내내 캐면 값이 내려갑니다.
- 하루에 한 번 **시황 충격**이 옵니다. 산지가 끊기거나 물량이 쏟아지거나, 유행이 오거나
  식습니다. 전체 공지되고 `/economy` 에 기록이 남습니다.

아이콘 툴팁 하나에 매수가·매도가·전일 대비·기준가 대비·재고·탄력성·시간당 채굴량·
**24일치 가격 그래프**(`▁▂▃▅▆▇`)·보유량·전량 매도 시 예상 금액이 전부 들어갑니다.
`/market price <품목>` 으로 같은 내용을 채팅으로도 봅니다.

### 은행
`/menu` → 은행, 또는 `/bank`. 입출금·정기예금·대출·신용등급이 있습니다.
**이자는 경제일(기본 20분)마다 붙고, 1년은 12경제일입니다.** 서버가 꺼져 있는 동안은
시간이 가지 않습니다 — 한 달 쉬었다고 파산해서 돌아오면 안 되니까요.

| | 이자 |
|---|---|
| 입출금 | 정책금리 − 1.5% |
| 정기예금 | 입출금 + 기간당 0.2%p (묶을수록 높음, **가장 싼 대출 금리를 넘지 못함**) |
| 대출 | 정책금리 + 3% + 신용 가산(0~20%) |

- **신용등급 A+~F** (점수 300~1000). 제때 갚으면 오르고, 연체하면 하루마다 깎입니다.
  등급이 한도 배수와 가산금리를 정하고, F 는 아예 대출이 막힙니다.
- **한도**는 레벨과 예금에서 나옵니다(`기본 + 레벨당 + 예금의 80%`) x 등급 배수. 지갑이
  아니라 쌓아 둔 것으로 정해지므로, 돈을 제일 안 필요로 하는 사람에게 제일 많이 빌려주는
  일이 없습니다. 여기에 DTI(총부채 한도)가 한 번 더 걸립니다.
- **연체하면** 가산금리 15%가 붙고, 예금이 있으면 **상계**되고, 그래도 남으면 시장에서
  물건을 팔 때 대금의 30%가 **압류**됩니다. 30일을 넘기면 채무불이행으로 처리되어
  신용점수가 바닥나고 한동안 대출이 막힙니다.
- **은행은 아무 돈이나 빌려주지 않습니다.** 예금 중 20%(지급준비율)는 반드시 남겨야 하고,
  나머지만 나갑니다. 예금이 없으면 대출도 없습니다 — 그래서 `/bank` 화면에 "대출 여력"이
  실제 숫자로 떠 있습니다.
- 모자라면 **중앙은행 상시 대출 창구**에서 끌어다 씁니다(기본 20만 한도). 이건 새로 찍은
  돈이라 통화량이 늘고, 정책금리만큼 이자를 물며, 여유가 생기는 대로 자동으로 갚습니다.
  서버를 연 첫날에도 대출이 되는 이유가 이것이고, 그 대가가 물가입니다.
- 은행 장부는 **대차대조표로 맞춰져 있습니다**: `자본 = (현금 + 대출채권) − (예금 + 중앙은행 차입)`.
  대출 이자는 수익, 예금 이자는 비용, 떼인 돈은 손실입니다. 자본이 크게 마이너스가 되면
  중앙은행이 발권해서 메우고 — 전체 공지됩니다.
- **회사 명의 대출**은 사람과 다른 자를 씁니다. 한도가 레벨·예금이 아니라 **회사 자산의
  60%** 이고(회사에는 레벨이 없습니다), 갚는 것도 회사 현금에서 나갑니다. 회사가 파산하면
  자산을 팔아 **은행부터** 갚고, 모자란 만큼은 은행 손실로 확정됩니다.
- **국채** `/bank bond <금액> [일수]` — 산 돈은 **국고로 들어가고** 만기에 국고가 원리금을
  갚습니다. 금리는 정책금리보다 조금 높고 예금보다도 높지만, **중도 환매가 없습니다.**
  국가가 돈을 빌리는 창구이자, 유통되는 골드를 묶어 두는 장치입니다 — 국고가 빌 때
  중앙은행이 발권하는 것 대신 쓸 수 있는 선택지입니다.
- 직업이 **신용점수**에 붙습니다. 상인·기업가·현자·파수꾼은 은행이 더 높게 봅니다
  (아래 직업 표).

### 경제 지표
`/menu` → 경제 지표, `/economy`, 또는 채팅으로 `/economy report`.
**전부 실제로 측정한 값**입니다. 어디에도 "그럴듯한 숫자"를 만들어 넣지 않았습니다.

| 지표 | 무엇을 재나 |
|---|---|
| 물가지수 CPI | 바스켓 품목들의 값을 가중평균해 첫날과 비교 |
| 물가상승률 | CPI 의 연율 (최소 3일치가 쌓여야 계산, 지수평활) |
| 정책금리 | **테일러 준칙**으로 매일 결정 |
| 통화량 M0/M1/M2 | 지갑 / +요구불예금 / +정기예금 |
| 통화승수 | M2 / M0 (한계 = 1 / 지급준비율) |
| GDP · 산출갭 | 하루 거래액과 그 추세와의 차이 |
| 화폐유통속도 V | 연 거래액 / M2 |
| 지니계수 | 순자산 불평등 (0 = 완전 평등) |
| 실업률 | 접속자 중 회사에 소속되지 않은 비율 |
| 주가지수 | 전 종목 시가총액을 첫날 = 1,000 으로 지수화 |
| 예대율 · 연체율 · 자기자본 | 은행 건전성 |
| 국채 잔액 · 발권 누적 | 재정과 통화 |

**금리는 이렇게 정해집니다.**

```
정책금리 = 중립금리 + 물가상승률
          + 0.5 x (물가상승률 − 물가목표)
          + 0.25 x 산출갭
```

물가가 목표보다 높으면 올려서 대출을 줄이고, 낮으면 내려서 풉니다. 하루 최대 1%p 씩만
움직이고 0.25%p 미만은 아예 움직이지 않습니다.

**그리고 돈이 실제로 물가에 닿습니다(MV = PQ).** 몬스터 처치·레벨업·업적·대출로 새 골드가
생기고, 세금·수수료·대출 상환으로 사라집니다. 그 차이가 생산 증가율을 넘으면 넘은 만큼
**물가 수준 전체가 올라갑니다**(반영률 60%, 하루 최대 3%). 이게 없으면 통화량은 화면에
뜨는 장식이고, 서버가 골드를 아무리 찍어도 빵값은 그대로입니다.

그래서 고리가 닫힙니다.

```
골드가 늘어난다 → 물가가 오른다 → 중앙은행이 금리를 올린다
   → 대출이 비싸진다 → 새로 생기는 돈이 줄어든다 → 물가 압력이 식는다
```

물가가 목표에서 5%p 이상 벗어나면 중앙은행이 **공개시장운영**까지 합니다. 비축 창고를
풀어 공급을 늘리거나(값 하락), 과잉 물량을 사들입니다(값 방어). 비축은 유한해서
바닥나면 지표판에 "개입 여력 없음"이라고 뜹니다 — 국가도 영원히 값을 떠받칠 수는 없습니다.

### 스탯 / 레벨
STR · DEX · VIT · AGI · LUCK. 레벨업마다 포인트를 받아 `/stats` 창에서 찍습니다.
찍은 값은 바닐라 어트리뷰트에 그대로 반영됩니다.

한 스탯이 한 가지만 하면 고를 이유가 없으므로, 스탯마다 **역할이 두세 개씩** 있습니다.

| 스탯 | 효과 | 20포인트 기준 |
|---|---|---|
| STR | 공격력, 공격 넉백, 최대 소지무게 | 공격력 +7 (다이아검 7 → 14), 넉백 +40%, 무게 +160 |
| DEX | 공격 속도, 채굴 속도, 휩쓸기 피해 | 초당 타격 +30%, 채굴 +16%, 휩쓸기 +20% |
| VIT | 최대 체력, 넉백 저항 | 체력 +40(20칸), 넉백 저항 +16% |
| AGI | 이동속도, 점프력, 안전 낙하 거리 | 이동 +24%, 점프 +14%, 낙하 3블록 더 |
| LUCK | 행운, **처치 보상 2배 확률** | 행운 +8, 골드 2배 확률 40% |

**LUCK 이 실제로 쓰이게 했습니다.** 바닐라 `luck` 어트리뷰트는 낚시 전리품 표에만
영향을 주기 때문에, 그것만으로는 아무도 찍지 않습니다. 이제 몬스터를 처치할 때
LUCK 에 비례한 확률로 **골드 보상이 2배**가 되고, 터지면 액션바에 `✦ 행운! 보상 2배`
가 뜹니다. 확률에는 상한(`economy.luck-double-chance-max`, 기본 60%)이 있습니다 —
"항상 2배"에 닿는 순간 그건 운이 아니라 **모두가 찍어야 하는 고정 배수**가 되고,
선택이 사라집니다.

#### 소프트캡 — 왜 한 스탯만 찍으면 손해인가

포인트당 효과가 끝까지 일정하면, 최적 전략은 언제나 **한 스탯에 전부 몰기**입니다.
그래서 `config.yml` 의 `stats.soft-cap`(기본 20)을 넘는 포인트는 **35%만** 적용됩니다.

```
실효값 = min(포인트, 20) + (포인트 - 20) × 35%

STR 20 → 실효 20     (공격력 +7.0)
STR 40 → 실효 27     (공격력 +9.5)   ... 포인트는 2배인데 효과는 1.36배
STR 20 + VIT 20 → 실효 20/20 (공격력 +7.0, 체력 +40)
```

40포인트를 한 곳에 몰면 27, 둘로 나누면 20+20 = 40 어치입니다. **넓게 찍는 쪽이 항상
이득이지만**, 특화가 필요한 상황(예: 무게가 모자란 광부)에서는 몰아 찍는 선택도
여전히 유효합니다. 그게 선택이 되도록 깎는 비율을 0 이 아니라 35%로 잡았습니다.

`/stats` 창은 찍은 포인트와 실효값을 같이 보여주고, 캡을 넘긴 스탯에는
`실효 31.9 — 20 초과분은 35%만 적용됩니다` 한 줄이 붙습니다.
`soft-cap: 0` 으로 두면 곡선이 꺼지고 예전처럼 완전 선형이 됩니다.

#### 레벨 곡선

XP는 몹 처치(15), 벌목한 원목(2), `/rpgcore givexp` 로 들어옵니다.
기본 곡선(`80 / 30 / 1.022`)은 이렇게 됩니다.

| | Lv2 | Lv10 | Lv20 | Lv30 | Lv50 | Lv100 |
|---|---|---|---|---|---|---|
| 필요 XP | 80 | 380 | 917 | 1,692 | 4,320 | 25,479 |
| 누적 | 80 | 2,270 | 8,660 | 21,795 | 80,335 | 708,856 |

레벨 50까지 누적 약 80,000 XP — 몹만 잡는다면 5,400마리입니다. 배수가 1.0(직선)이면
50레벨이 10레벨과 똑같은 무게로 느껴지지만, 1.022 에서는 마지막 레벨이 10레벨의 10배가
들어서 **초반은 빠르게 흐르고 후반 레벨 하나하나가 사건이 됩니다.**

**레벨은 체력을 조금만 줍니다**(레벨당 1). 예전처럼 레벨당 2였을 때는 레벨 50에서
아무 것도 안 찍고 체력 120(60칸)이 되어 **VIT 를 찍을 이유가 사라졌습니다.**
**최대 레벨**과 **경험치 곡선**은 `settings.yml`, 스탯 계수는 `config.yml` 의
`stats:` 블록에서 정합니다.

### 직업 (클래스)
`/job` 으로 고릅니다. 직업은 **스탯 보너스 + 어트리뷰트 + 경험치 배율 + 소지무게**를 줍니다.

직업은 **3단계 15종 + 경제 직업 4종, 모두 19종**입니다. 위로 갈수록 강해지는 게 아니라,
**더 뾰족해집니다.**

**1단계 (레벨 1)** — 방향만 정해 줍니다. 약점이 없습니다.

| 직업 | 주는 것 |
|---|---|
| 전사 | STR+3 VIT+2, 최대체력 +4, 넉백저항 +15%, 무게 +30 |
| 궁수 | DEX+3 AGI+2, 이동속도 +8%, 상호작용 사거리 +0.5 |
| 광부 | STR+2 VIT+1, 채굴 +25%, 수중 채굴 +100%, 산소 +2, 무게 +70, XP x1.1 |
| 나무꾼 | STR+2 DEX+2, 채굴 +15%, 무게 +50, XP x1.15 |
| 어부 | LUCK+4 VIT+1, 산소 +4, 수중 이동 +60% |

**2단계 (레벨 12)** — 한 가지를 확실히 잘하는 대신 **다른 하나를 포기합니다.**

| 직업 | 주는 것 | 포기하는 것 |
|---|---|---|
| 기사 | VIT+4 STR+2, 방어 +4, 강도 +2, 체력 +6, 넉백저항 +40%, 무게 +60 | 이동속도 −6% |
| 도적 | AGI+4 LUCK+3, 이동 +14%, 공속 +12%, 웅크리기 +50% | 최대체력 −4 |
| 사냥꾼 | DEX+3 AGI+3 LUCK+1, 사거리 +1.0, 안전낙하 +3, 이동 +6% | — (범용형) |
| 대장장이 | STR+4 VIT+2, **무게 +160**, 방어 +2, 채굴 +10% | 이동속도 −4% |
| 탐험가 | AGI+5 LUCK+1, 이동 +18%, 점프 +15%, 안전낙하 +5, 계단 +0.5 | 공격력 −1 |

**3단계 (레벨 30)** — 극단적인 특화. **약점이 분명한 대신 강점이 큽니다.**

| 직업 | 주는 것 | 포기하는 것 |
|---|---|---|
| 수호자 | VIT+7 STR+2, 방어 +7, 강도 +4, 체력 +12, 넉백저항 +70%, 폭발저항 +50%, 무게 +120 | 이동속도 −10% |
| 광전사 | STR+7 DEX+3, 공격력 +30%, 공격넉백 +50%, 휩쓸기 +50%, 무게 +40 | 체력 −6, 방어 −2 |
| 암살자 | DEX+6 AGI+4, 공속 +30%, 이동 +20%, 웅크리기 +80% | **체력 −8** |
| 현자 | LUCK+6 VIT+2 DEX+2, 행운 +3, **XP x1.4** | 공격력 −15% |
| 파수꾼 | STR+3 VIT+4 DEX+3 AGI+2, 방어 +3, 체력 +6, 무게 +80, XP x1.1 | — (균형형, 어느 쪽도 최고는 아님) |

**경제 직업** — 싸우는 대신 버는 쪽. 전투 능력은 거의 없고, 대신 경제에 붙습니다.

| 직업 | 요구 | 주는 것 |
|---|---|---|
| 상인 | 1 | LUCK+3 AGI+1, 무게 +40, **시장 수수료 −35%**, 신용점수 +40 |
| 농부 | 1 | VIT+2 STR+1, 체력 +2, 무게 +50, XP x1.05, 공장 생산 +15%, 임금 +15% |
| 기업가 | 12 | LUCK+2 AGI+2, **공장 생산 +22%**, 임금 +25%, **신용점수 +70**, 수수료 −10% |
| 건축가 | 12 | DEX+2 VIT+2, 무게 +60, **청사진 시공비 −35%**, 공장 생산 +8% |

**직업이 경제에 붙는 다섯 가지 수치**입니다. 전투 직업에도 걸려 있습니다 — 광부·나무꾼·
어부는 공장 생산에, 대장장이는 가공 공장과 건축에, 도적·탐험가는 시장 수수료에,
현자·파수꾼은 신용점수에.

| 수치 | 하는 일 |
|---|---|
| `market-fee-discount` | 시장 거래세를 그만큼 깎습니다 (영수증에 "직업 할인" 으로 표시) |
| `factory-bonus` | **고용주의** 공장 생산량을 올립니다. 직원 전원 합산, 상한 50% |
| `wage-bonus` | 자기 일당을 올립니다 |
| `build-discount` | 청사진 **시공비**(자재값 말고 인건비)를 깎습니다 |
| `credit-bonus` | 은행 신용점수에 더해집니다 (한도와 가산금리가 같이 움직입니다) |

`factory-bonus` 가 **고용주**에게 붙는 것이 요점입니다. 광부를 고용한 광산 회사가 실제로
더 캐냅니다 — 회사가 사람을 뽑을 이유가 임금 지출 외에 하나 더 생깁니다.

몇 가지 설계 의도:

- **3단계가 1단계의 상위 호환이 아닙니다.** 암살자는 체력이 8(4칸) 깎이고, 광전사는
  방어구를 벗다시피 합니다. 레벨 30에 도달했다고 무조건 갈아타는 게 정답이 아니게
  하려고 실제 페널티를 넣었습니다.
- **직업 보너스도 소프트캡에 함께 들어갑니다.** 이미 STR 20을 찍은 사람이 광전사
  (STR+7)를 고르면 그 7은 35%만 들어옵니다. 자기가 안 찍은 쪽을 메워 주는 직업이
  포인트 효율이 더 좋습니다 — 직업 선택에 실제 고민이 생깁니다.
- **`multiply` 는 합계에 대한 비율**이라 `add` 보다 훨씬 강합니다. 그래서 이동속도처럼
  넘치기 쉬운 값에는 작게(6~20%), 무게처럼 안전한 값에는 크게 잡았습니다.

직업이 주는 스탯은 직접 찍은 포인트 **위에 더해집니다**. `/stats` 창에서 `VIT: 5 (2 +3 직업)`
처럼 분리해서 보여줍니다. 직업을 바꾸면 이전 직업의 보너스는 전부 해제됩니다.
전부 `jobs.yml` 에 있으므로 코드 수정 없이 추가·수정할 수 있습니다.

### 순위표 (리더보드)
`/leaderboard [항목]` — 스코어보드에 기록되는 값은 전부 순위로 볼 수 있습니다.

| 묶음 | 항목 |
|---|---|
| 성장 | `level`, `gold` |
| 스탯 | `str` `dex` `vit` `agi` `luck` |
| 진행도 | `mob-kills` `blocks-mined` `ores-mined` `logs-chopped` `fish-caught` `duels-won` `gold-earned` `collected` |

자기 순위가 표시 범위 밖이면 맨 아래에 따로 붙여줍니다.

데이터는 이미 쓰고 있는 **스코어보드 미러**에서 읽습니다. 별도 저장소가 없고,
**접속 중이 아닌 플레이어도 집계**됩니다. 결과는 몇 초간 캐시되므로 명령어를 연타해도
서버에 부담이 없습니다.

### 파티
`/party create [이름]` 으로 만들고 초대합니다. **파티는 서버를 재시작해도 유지됩니다.**

- **이름** — 파티마다 고유한 이름을 붙입니다. 이름은 파티 채팅 접두사, 초대 문구, `/party list`
  에 그대로 쓰입니다. `/party name <새이름>` 으로 바꿉니다(파티장만). 색코드는 제거되고,
  이미 쓰이는 이름이나 길이 초과(기본 16자)는 거부됩니다.
- **경험치 공유** — 파티가 얻은 XP 는 사거리(기본 50블록) 안에 있고 **접속 중인** 파티원끼리만
  나눕니다. 오프라인 파티원은 몫도 받지 않고 인원 보너스에도 들어가지 않습니다.
  `총량 = 원래 XP × (1 + 0.05 × (접속 인원-1))`
  예) 3명 접속 중 10 XP → 11 XP → 각자 4 XP. 한 명이 나가면 → 10.5 XP → 각자 5 XP.
- **아군 공격 차단** — 기본적으로 파티원끼리는 근접·투사체 피해가 들어가지 않습니다.
- **파티 채팅** — `/p <메시지>` 는 거리와 무관하게 접속 중인 파티원 전체에게 갑니다.
- 오프라인 파티원도 `/party list` 에 보이고 추방할 수 있습니다. 파티장이 `/party leave` 하면
  다음 사람에게 파티장이 넘어가고, 파티를 없애려면 `/party disband` 를 씁니다.

### 플레이어 간 거래
`/trade <플레이어>` 로 요청하고, 상대가 `/trade accept` 하면 **양쪽이 같은 상자 UI 하나**를
함께 봅니다.

```
 내가 내놓는 것        상대가 내놓는 것
 ┌───────────┐ │ ┌───────────┐
 │ ■ ■ ■ ■   │ │ │   ■ ■ ■ ■ │
 │ ■ ■ ■ ■   │ │ │   ■ ■ ■ ■ │   왼쪽 4칸 = 내 물건
 │ ■ ■ ■ ■   │ │ │   ■ ■ ■ ■ │   오른쪽 4칸 = 상대 물건
 │ ■ ■ ■ ■   │ │ │   ■ ■ ■ ■ │
 └───────────┘ │ └───────────┘
   [내 확정]    │   [상대 확정]
```

- 화면을 **하나만** 쓰므로 한쪽에게만 다르게 보이는 일이 구조적으로 불가능합니다.
- 자기 칸에만 물건을 올릴 수 있습니다. 상대 칸 클릭, 드래그, 더블클릭 모으기는 전부 막힙니다.
- 물건이 바뀌면 **양쪽 확정이 자동으로 풀립니다.** 확정 직전에 몰래 바꿔치기할 수 없습니다.
- 양쪽이 확정하면 교환됩니다. 받을 공간이 모자라면 **아무것도 옮기지 않고** 알려줍니다.
- 창을 닫거나, 접속을 종료하거나, 죽거나, `/trade cancel` 하거나, 서버가 꺼지면
  **올려둔 물건은 전부 주인에게 돌아갑니다.**

### 업적과 칭호
목표를 달성하면 골드/경험치 보상과 **칭호**가 들어옵니다. 칭호는 `/titles` 에서 골라
이름 옆에 붙입니다 — 머리 위 이름표와 Tab 목록 양쪽에 나옵니다.

**업적 50개, 칭호 34개**가 기본으로 들어 있습니다. 도감 20개 분류에 걸린 칭호까지 하면
서버에 **칭호가 54개** 돌아다닙니다 (`/rpgcore check` 가 세어 줍니다). 대부분 하나의 기준을 여러 단계로
나눠 두었으므로, 처음 한 칸은 금방 채워지고 마지막 칸은 오래 걸립니다.

|---|---|---|---|
| 레벨 | 9 | 100 | `[한계를 넘은 자]` |
| 몬스터 처치 | 5 | 20,000마리 | `[종결자]` |
| 대결 승리 | 5 | 200승 | `[무패의 전설]` |
| 블록 채굴 | 4 | 100,000개 | `[대굴착자]` |
| 광석 채굴 | 4 | 5,000개 | `[심층 채굴자]` |
| 누적 골드 | 4 | 1,000,000G | `[황금 손]` |
| 도감 등록 | 4 | 250종 | `[박물학자]` |
| 원목 벌목 | 3 | 10,000개 | `[숲을 민 자]` |
| 물고기 낚기 | 3 | 2,500마리 | `[바다의 인내]` |

경제 업적 9개는 **싸우지 않고도 업적을 채울 수 있게** 하려고 넣었습니다. 시장에서
사고판 금액, 주식 배당으로 받은 금액, 청사진으로 실제로 올라간 블록 수를 셉니다.

그 중 **5개는 서버에서 딱 한 명**만 가져가는 기록입니다 (`first-only`) — 레벨 25
`[개척자]`, 레벨 60 `[선구자]`, 25승 `[초대 챔피언]`, 광석 2,500개 `[광맥왕]`,
도감 200종 `[초대 관장]`. 이건 **경쟁**이지 목표가 아니라서, 두 번째로 달성한 사람은
아무것도 받지 못합니다.

- `first-only: true` 를 붙이면 **서버에서 딱 한 명**만 가져가는 기록이 됩니다.
  먼저 달성한 사람의 이름이 `records.yml` 에 남고 `/achievements` 에 표시됩니다.
  (동시에 달성해도 기록을 먼저 쓴 쪽만 인정되므로 두 명이 같은 최초를 가져갈 수 없습니다.)
- 칭호가 걸린 업적과 서버 최초 업적은 서버 전체에 알립니다.
- 창작 모드로 부순 블록과 낚은 물고기는 세지 않습니다.
- `/achievements` 로 항목별 진행도를, `/titles` 로 칭호 목록(못 얻은 것은 회색)을 봅니다.

### 골드
업적 보상과 몬스터 처치·레벨업으로 들어오고, **경매장에서 쓰고** 대결에 걸 수 있는 재화입니다.
스코어보드(`rpgcore.gold`)에 저장되므로 **경제 플러그인이 필요 없고** `/scoreboard` 로도
읽고 쓸 수 있습니다. `/gold` 로 확인, `/pay <플레이어> <금액>` 으로 주고받고,
`/rpgcore givegold` 로 지급·회수합니다.

주고받은 골드는 **'누적 획득'에 들어가지 않습니다.** 둘이서 같은 돈을 주거니 받거니 해서
`gold-earned` 업적을 파밍할 수 없습니다. `/pay` 자체를 막으려면
`economy.allow-player-transfer: false`.

### 수집 도감
**20개 분류, 363종**을 모으는 도감입니다. `/collection` 으로 엽니다.

| 묶음 | 분류 |
|---|---|
| 자원 | 원목 · 나무 가공 · 광물 · 주괴와 보석 · 돌과 광맥 |
| 자연 | 작물 · 꽃 · 묘목 · 버섯과 균사 · 산호 · 물고기 |
| 전리품 | 몬스터 전리품 · 머리 |
| 제작 | 양털 · 염료 · 방어구 한 벌 · 연장 · 음악 디스크 |
| 차원 | 네더 · 엔드 |

**분류를 다 채우면 칭호가 나옵니다** — 20개 분류 전부에 칭호가 걸려 있어서,
도감 자체가 칭호 20개짜리 콘텐츠입니다. 난이도에 맞춰 보상을 달리 잡았습니다:
돌과 광맥 300G, 음악 디스크 3,000G(21종을 전부 모아야 합니다), 엔드 4,000G.

- **인벤토리에 들어오기만 하면 등록**됩니다. 캐든, 만들든, 낚든, 상자에서 꺼내든 모두 인정.
- 한 장을 다 모으면 칭호와 보상이 들어오고 서버 전체에 알립니다.
- 모은 칸은 아이템 그대로, 못 모은 칸은 회색 유리로 보여 한눈에 진행도가 읽힙니다.
- 한 분류가 한 화면(45칸)을 넘으면 자동으로 쪽이 나뉩니다. `#minecraft:logs` 같은
  태그를 통째로 넣어도 뒤쪽이 잘리지 않습니다.
- 기존 서버에 처음 설치하면 **이미 들고 있던 물건은 조용히 등록**됩니다. 접속하자마자
  수십 줄이 쏟아지거나, 몇 달 전에 채운 칸으로 보상이 한꺼번에 나가지 않습니다.

### 1:1 대결
`/duel <플레이어> [건 것]` — 양쪽이 동의하고 같은 것을 걸어야 시작됩니다.

- 건 것을 비우면 그냥 대결, 숫자면 **골드**, `hand` 면 **손에 든 아이템**입니다.
  수락하는 쪽은 같은 것(아이템이면 같은 종류·같은 개수)을 내야 합니다.
- 시작할 때 양쪽에서 **미리 빼둡니다.** 걸어 둔 것은 대결 중에 쓰거나 버리거나
  거래로 넘길 수 없고, 서버가 갑자기 내려가도 그대로 돌려받습니다.
- **죽지 않습니다.** 치명타가 들어오는 순간 피해를 취소하고 승패로 처리하므로
  진 쪽도 아이템을 떨어뜨리지 않습니다. 끝나면 양쪽 다 체력이 회복됩니다.
- 시작 전 **3초 카운트다운**이 있고 그동안은 서로 때릴 수 없습니다. 수락하자마자
  한 대 맞고 시작하는 일이 없습니다.
- 시작할 때 양쪽 **체력을 채웁니다.** 한쪽이 반 칸이라 지는 대결은 대결이 아니니까요.
  (`duel.countdown-seconds`, `duel.heal-before-start` 로 끕니다)
- 도중에 접속을 끊으면 기권패입니다. 제한 시간(기본 5분)이 지나면 무승부로 끝나고
  건 것은 그대로 돌아갑니다.
- 파티원끼리도 대결할 수 있습니다(아군 공격 차단보다 대결이 우선).
- 월드의 PvP 가 꺼져 있으면 **신청 단계에서** 막힙니다.

### 소지 무게
인벤토리 + 방어구 + 보조손 41칸을 `개수 × 등급 무게` 로 계산합니다.
부하율에 따라 4단계이며, 단계가 바뀔 때만 어트리뷰트를 건드립니다.

| 부하율 | 이동속도 | 점프 | 추가 |
|---|---|---|---|
| ~70% | – | – | – |
| 70~100% | -10% | -15% | – |
| 100~130% | -25% | -40% | 허기 |
| 130%~ | -50% | -70% | 허기 + 채굴 피로 |

### 장비 내구도 → 성능
낡은 무기는 약하게 때리고, 낡은 방어구는 덜 막고, 낡은 도구는 느리게 캡니다.
남은 내구도가 `full-performance-above`(기본 80%) 이상이면 페널티 없음, 그 아래로는
0%까지 `minimum-performance`(기본 50%)로 직선 감소합니다. 예) 내구도 60% → 성능 87%.

| 대상 | 기준 | 적용 |
|---|---|---|
| 근접 공격 / 채굴 속도 | 주 손 아이템 | `attack_damage`, `block_break_speed` |
| 방어력 | 착용 방어구 **평균** | `armor`, `armor_toughness` |
| 원거리 피해 | 발사한 활·석궁·삼지창 | 투사체 기본 피해량 |

아이템 자체는 건드리지 않고 플레이어 어트리뷰트에만 걸리므로, 수리하면 성능이 그대로 돌아옵니다.
원거리는 **발사 시점** 무기 상태를 투사체에 새깁니다.

### 모루 커스텀 강화
왼쪽 칸에 장비, 오른쪽 칸에 재료. **경험치 레벨을 쓰지 않고 반복 횟수 제한도 없습니다.**
바닐라의 "수리 비용이 너무 비쌉니다" 누적 제한도 걸리지 않습니다.

| 조합 | 재료 | 효과 |
|---|---|---|
| 날 세우기 | 부싯돌 2 | 날카로움 +1 |
| 성화 각인 | 발광석 가루 3 | 강타 +1 |
| 독 바르기 | 거미 눈 3 | 벌레 죽이기 +1 |
| 기계 정비 | 레드스톤 4 | 효율 +1 |
| 철판 덧대기 | 철 블록 1 | 보호 +1 |
| 흑요석 담금질 | 흑요석 2 | 내구성 +1 |
| 숫돌 정비 | 숫돌 1 | 내구도 +25% |

조합법에 걸리지 않는 조합은 **바닐라 모루 그대로**입니다 — 같은 재료 수리, 인챈트북 합치기,
이름 변경 모두 정상 동작합니다. 내구도 페널티와 맞물려 **수리 = 성능 회복**입니다.

### 연쇄 벌목
도끼로 원목을 캐면 이어진 같은 원목이 전부 순차 제거됩니다. **가지와 대각선 줄기까지 따라갑니다**
— 참나무·정글나무 가지, 아카시아의 비스듬한 줄기, 2x2 굵은 나무 모두 한 번에 잘립니다.

번지는 범위는 두 가지로 묶여 있습니다.
- **캔 블록보다 아래로는 내려가지 않습니다** — 바닥에 깔린 원목이나 옆 나무 밑동을 파먹지 않습니다.
- **가로 반경 제한**(`max-horizontal-radius`, 기본 5) — 원목이 줄지어 있어도 옆 나무로 옮겨붙지 않습니다.

큐를 틱당 몇 블록씩만 소비하므로 대형 나무에서도 렉이 없습니다.
웅크리면 비활성, 크리에이티브 제외, `max-blocks` 상한 적용.
6면 원목(`oak_wood` 등)은 기본 목록에 없어 원목 건축물은 안전합니다.

### 근접 채팅
설정한 거리 안의 플레이어에게만 채팅이 전달됩니다. 플레이어가 입력한 `&` 색코드는
그대로 텍스트로 나가므로 채팅을 꾸미거나 위장할 수 없습니다.

### 이름표 · 플레이어 목록
머리 위 이름표와 Tab 플레이어 목록에 파티·칭호·레벨·직업이 함께 나옵니다.

```
머리 위   [푸른사슴] [강태공] Alpha Lv.6 전사
Tab 목록  [푸른사슴] [강태공] Alpha Lv.6
```

- 파티가 없거나 칭호·직업이 없으면 **그 조각만 통째로 빠집니다** — 빈 괄호가 남지 않습니다.
- 무엇을 보여줄지는 두 곳에서 따로 정합니다(기본값: 목록에는 직업 미표시).
- 스코어보드 팀 기능으로 붙이므로 **베드락(Geyser)에서도 똑같이 보이고**, 별도 패킷을
  매 틱 쏘지 않습니다. 레벨·파티·직업이 실제로 바뀔 때만 갱신됩니다.
- 접속을 끊으면 붙였던 팀도 같이 지워집니다(월드 스코어보드에 쌓이지 않음).
  다른 플러그인이 이름표를 관리한다면 `features.nameplate` 를 끄면 됩니다.

### 아이템 무게 툴팁
아이템 설명 맨 아래에 작은 회색 글씨로 `무게 8` 한 줄이 붙습니다.

- **1개당 무게**입니다. 개수와 무관한 값이라야 같은 아이템끼리 계속 겹쳐집니다.
- 바닥에 떨어진 아이템, 상자에서 꺼낸 아이템에도 같은 줄이 붙으므로 **묶음이 갈라지지 않습니다.**
- 다른 플러그인이 넣은 설명이나 플레이어가 붙인 이름은 건드리지 않고, 이 한 줄만 관리합니다.
- 무게 설정을 바꾸고 `/rpgcore reload` 하면 줄도 따라서 갱신되고, 기능을 끄면 다시 지워집니다.

### Discord 연동

서버에서 일어난 일을 디스코드 채널로 보냅니다. **봇을 만들 필요 없이 웹후크 주소 하나**면
되고, 다른 플러그인도 라이브러리도 필요 없습니다.

**설정 (2분)**

1. 디스코드에서 알림을 받을 채널 우클릭 → **채널 편집 → 연동 → 웹후크 → 새 웹후크**
2. **[웹후크 URL 복사]**
3. `config.yml` 의 `discord.webhook-url` 에 붙여넣고 `enabled: true`
4. `/rpgcore reload`

보내는 것과 그 모양:

| 알림 | 색 | 보기 |
|---|---|---|
| 서버 열림 | 초록 | 🟢 서버가 열렸습니다 · Paper 26.2 · RPGCore 2.6.0 |
| 서버 닫힘 | 빨강 | 🔴 서버가 닫혔습니다 · 가동 시간 3시간 12분 |
| 접속 / 퇴장 | 초록 / 회색 | Steve 님이 접속했습니다 · 접속 중 4명 |
| 사망 | 빨강 | 💀 Steve was slain by Zombie · Lv.23 · world |
| 레벨업 | 블러플 | ⬆️ Steve 님이 Lv.30 이 되었습니다 |
| 업적 | 금색 | 🏆 Steve 님이 [광맥왕] 을(를) 달성했습니다 · 2000G · 칭호 [광맥왕] |
| 서버 최초 업적 | 자홍 | 🥇 Steve 님이 … 을(를) 서버 최초로 달성! |

**한 줄에 하나씩, 색으로 구분합니다.** 임베드의 왼쪽 색 막대가 종류를 대신하므로 글을
읽기 전에 무슨 일인지 알 수 있고, 플레이어 머리 아이콘이 붙어서 누구인지는 얼굴로
먼저 읽힙니다. 사망은 **바닐라 사망 메시지를 그대로** 옮깁니다 — 원인과 가해자가 이미
들어 있어서 다시 쓰면 정보만 잃습니다.

#### 채널이 잠기지 않게 하는 것들

알림을 다 보내면 채널이 못 읽게 됩니다. 그래서 세 겹으로 거릅니다.

- **레벨업은 걸러서 보냅니다.** 초반 레벨은 몇 분에 한 번씩, 그것도 인원수만큼 올라옵니다.
  기본값은 `minimum-level: 10` 과 `only-multiples-of: 5` — Lv.10 밑은 보내지 않고, 그
  위로는 5의 배수만 보냅니다. **최대 레벨 도달은 이 조건과 상관없이 항상** 보냅니다.
- **업적은 게임 안 공지 규칙을 따릅니다.** 서버 전체에 알릴 만한 것(서버 최초 기록,
  칭호가 걸린 업적)만 갑니다. 자잘한 단계까지 원하면 `all-achievements: true`.
- **묶어서 보냅니다.** 0.4초 안에 생긴 알림은 한 메시지에 최대 10개까지 함께 담깁니다.
  한 전투에서 열 명이 죽으면 디스코드 메시지도 **열 개가 아니라 하나**입니다.

`events` 아래에서 종류별로 끄고 켤 수 있습니다.

#### 서버가 느려지지 않게 하는 것들

남의 서버로 HTTP 요청을 보내는 일이라, **메인 스레드는 절대 기다리지 않습니다.**

- 전송은 전용 스레드(`RPGCore-discord`)에서 합니다. Bukkit 의 비동기 스케줄러가 아닌
  이유는 파일 저장과 같습니다 — 그 스케줄러는 메인 스레드 박동에서 일을 넘기므로,
  **메인 스레드가 바쁘거나 종료 중일 때는 돌지 않습니다.** 종료 알림이 필요한 순간이
  정확히 그때입니다.
- 대기열은 상한이 있고(256건), 차면 **가장 오래된 것부터 버립니다.** 디스코드가 죽어도
  힙이 늘지 않고 호출한 쪽이 멈추지 않습니다.
- 429(속도 제한)는 디스코드가 알려준 시간만큼 기다렸다가 다시 보냅니다. 404/401
  (지워졌거나 잘못된 웹후크)는 재시도하지 않고 **경고를 한 번만** 남깁니다.

#### 주소는 비밀번호입니다

웹후크 주소를 아는 사람은 누구나 그 채널에 **서버인 척 글을 쓸 수 있습니다.**

- 플러그인은 이 주소를 **로그에도, `/rpgcore check` 에도 찍지 않습니다.** 점검 화면에는
  `웹훅 설정됨` 이라고만 나옵니다.
- 실수로 공개했다면 디스코드에서 그 웹후크를 지우고 새로 만드세요. 주소만 바꾸면 됩니다.
- 플레이어 이름과 업적 이름은 디스코드 마크다운으로 **이스케이프해서** 보내고, 모든
  메시지에 `allowed_mentions` 를 비워 보냅니다. 이름에 `@everyone` 이 들어 있어도
  서버 전체에 알림이 가지 않습니다.

> **한쪽 방향입니다** (마인크래프트 → 디스코드). 디스코드에 친 글을 게임 채팅으로
> 가져오려면 상시 연결된 봇이 필요하고, 그건 웹후크로 되는 일이 아닙니다.

## 설정

설정은 `plugins/RPGCorePlugin/` 안의 **파일 3개**로 나뉩니다. 목적이 달라서 나눠 뒀으니,
바꾸고 싶은 게 어디 있는지만 알면 됩니다.

| 파일 | 무엇이 들어 있나 | 언제 여나 |
|---|---|---|
| **`settings.yml`** | 최대 레벨, 경험치 곡선, 인챈트 한계, 기능 on/off | **대부분 여기만 보면 됩니다** |
| **`jobs.yml`** | 직업 정의 | 직업을 만들거나 고칠 때 |
| **`achievements.yml`** | 업적과 그 보상·칭호 | 목표를 만들거나 고칠 때 |
| **`collection.yml`** | 도감 분류와 수집 대상 | 도감에 항목을 넣을 때 |
| **`economy.yml`** | 시장 품목표(시간당 채굴량·탄력성·물가 가중치), 임금과 초기 공급, 스프레드·거래세, 은행 금리·지급준비율·신용등급, 중앙은행 물가목표와 테일러 준칙 | 경제를 손볼 때 |
| **`corporations.yml`** | 공장 25종(생산량·원료·건설비·유지비), 창업비·임금·법인세, 주식·배당·인수 규칙, **부실과 파산 기준**, **공기업 설립·민영화 기준**, 기초 기업 8곳 | 기업을 손볼 때 |
| `config.yml` | 아이템 무게 분류, 모루 조합법, 벌목 대상, 골드, 대결, GUI, 채팅 | 세부 조정이 필요할 때 |

> `market.yml` · `bank.yml` · `macro.yml` · `companies.yml` · `blueprints.yml` ·
> `construction.yml` 은 **설정이 아니라 상태**입니다(재고, 가격,
> 예금, 대출, 물가 이력). 플러그인이 계속 다시 쓰므로 손으로 고치지 마세요. 경제 설정은
> 전부 `economy.yml` 에 있습니다.
>
> `records.yml` 은 플러그인이 직접 씁니다. '서버 최초' 업적을 누가 가져갔는지 담겨
> 있으니 손으로 고치지 마세요. 지우면 그 기록이 다시 열립니다.

고친 뒤 **`/rpgcore reload`** 하면 재시작 없이 반영됩니다.

> 자동으로 옮겨오고 로그에 알려줍니다.

### settings.yml — 자주 바꾸는 것

```yaml
level:
  max: 0                # 최대 레벨. 0 이면 제한 없음
  xp-base: 80           # 레벨 2 가 되는 데 필요한 XP
  xp-growth: 30         # 레벨이 오를 때마다 추가로 붙는 XP
  xp-multiplier: 1.022  # 레벨당 곱해지는 배수
  points-per-level: 1
  starting-points: 5

xp-sources:
  per-mob-kill: 15
  per-tree-log: 2

enchant:
  respect-vanilla-limits: false   # true 면 바닐라 최대 레벨까지만
  max-level: 255                  # 위가 false 일 때의 상한

features:               # 끄면 관련 명령어도 막힙니다
  jobs: true
  parties: true
  trading: true
  leaderboard: true
  tree-felling: true
  durability-scaling: true
  anvil-recipes: true
  proximity-chat: true
  hud: true
  nameplate: true         # 머리 위 이름표
  tablist: true           # 플레이어 목록(Tab)
  item-weight-lore: true  # 아이템 설명의 무게 한 줄
  achievements: true      # 업적과 칭호
  collection: true        # 수집 도감
  duels: true             # 1:1 대결
```

**최대 레벨** — `level.max` 에 닿으면 더 이상 XP 가 쌓이지 않습니다. 남은 XP 를 쌓아두지 않으므로,
나중에 상한을 올려도 전원이 한꺼번에 레벨업하는 일은 없습니다.

**레벨 배수** — 다음 레벨까지 필요한 XP 는 이렇게 계산됩니다.

```
(xp-base + (현재레벨-1) × xp-growth) × (xp-multiplier ^ (현재레벨-1))
```

`xp-base: 80`, `xp-growth: 30` 기준으로 배수만 바꿔 보면:

| xp-multiplier | Lv2 | Lv10 | Lv20 | Lv50 |
|---|---|---|---|---|
| `1.0` (직선) | 80 | 320 | 620 | 1,520 |
| `1.022` (**기본**) | 80 | 380 | 917 | 4,320 |
| `1.05` (가파름) | 80 | 472 | 1,492 | 15,809 |
| `1.5` (아주 가파름) | 80 | 8,201 | 916,292 | 4,300억 |

**인챈트 한계** — 모루 커스텀 강화로 올릴 수 있는 상한입니다.
`respect-vanilla-limits: true` 면 날카로움 5, 보호 4 처럼 바닐라 최대치에서 멈춥니다.
`false` 면 `max-level`(최대 255)까지 계속 올라갑니다. 조합법마다 `max-level` 을 따로 적으면
**둘 중 낮은 쪽**이 적용됩니다.

### jobs.yml — 직업 만들기

`list:` 아래에 블록을 하나 더 붙이면 끝입니다. 코드 수정은 필요 없습니다.

```yaml
allow-change: true        # false 면 한 번 고르면 못 바꿈
change-cost-levels: 0     # 변경 시 소모할 바닐라 경험치 레벨
menu-title: "&8직업 선택"

list:
  mage:                          # 이게 /job <id> 의 id 입니다
    name: "&5마법사"
    icon: minecraft:blaze_rod
    description:
      - "&7설명 줄."
    min-level: 15                # 이 RPG 레벨부터 선택 가능
    stat-bonus:                  # 직접 찍은 포인트 위에 더해짐
      luck: 5
      dex: 2
    weight-bonus: 0              # 최대 소지무게에 더하기
    xp-multiplier: 1.2           # 획득 경험치 배율
    attributes:
      add:                       # 고정값 더하기
        max_health: 2
      multiply:                  # 합계에 비율 곱하기 (0.1 = +10%)
        movement_speed: 0.05
```

`attributes` 에는 **바닐라 어트리뷰트 ID 를 그대로** 씁니다:
`max_health` `attack_damage` `attack_speed` `armor` `armor_toughness`
`movement_speed` `knockback_resistance` `block_break_speed` `luck` `jump_strength` 등.
이 서버에 없는 ID 는 경고만 남기고 무시하므로 설정이 통째로 깨지지 않습니다.

### economy.yml — 경제

시장·은행·중앙은행이 전부 이 파일 하나입니다. 자주 만질 만한 것만 추리면 이렇습니다.

```yaml
clock:
  day-minutes: 20        # 경제일 1일 = 실시간 20분 (이자와 지표가 이 단위로 움직임)
  days-per-year: 12      # 1년 = 12경제일. 줄이면 이자가 빨리 붙습니다

market:
  hourly-wage: 1200      # 기준가 = 시급 / 시간당 채굴량 x 수요계수
  initial-supply-hours: 24
  reference-players: 10  # 초기 공급 = 시간당 채굴량 x 24 x 10
  spread-percent: 6      # 살 때와 팔 때의 차이. 0 이면 무한 차익이 생깁니다
  sales-tax-percent: 5   # 거래세. 국고로 들어가며 유통에서 사라집니다
  volatility-percent: 2  # 하루 등락폭
  treasury-start: 3000000  # 시장이 매입에 쓸 수 있는 돈

bank:
  reserve-ratio-percent: 20    # 통화승수 한계 = 1 / 이 값 = 5배
  loan-margin-percent: 3.0     # 대출금리 = 정책금리 + 이것 + 신용 가산
  central-bank-facility: 200000  # 예금이 없을 때 끌어다 쓰는 한도(= 발권)
  corporate-limit-percent: 60  # 회사 대출 한도 = 회사 자산의 이 비율
  bond-premium-percent: 0.5    # 국채 금리 = 정책금리 + 이것
  bond-max-days: 30            # 국채 최장 만기
  bond-total-limit: 5000000    # 국채 발행 잔액 상한

macro:
  inflation-target-percent: 2.0
  taylor-inflation-weight: 0.5
  taylor-output-weight: 0.25
  money-pass-through-percent: 60  # 통화 증가분 중 물가로 가는 비율 (MV=PQ)

items:
  # per-hour 하나만 적으면 기준가와 초기 공급이 둘 다 여기서 나옵니다
  diamond: { category: mineral, per-hour: 18, demand: 1.8, elasticity: 1.3, basket: 3 }
  wheat:   { category: farm,    per-hour: 620, demand: 1.0, elasticity: 0.6, basket: 3 }
```

- **품목을 추가**하려면 `items:` 에 한 줄만 넣으면 됩니다. 가격은 적지 않습니다.
- **물가를 재는 장바구니**는 `basket` 이 0 보다 큰 품목들입니다. 실제로 많이 쓰는 것에만
  가중치를 주세요.
- **서버가 크면** `reference-players` 를 올리세요. 모든 품목의 공급이 같은 비율로 따라갑니다.
- **경제를 통째로 끄려면** `settings.yml` 의 `features.market` / `features.bank` 를 `false` 로.

`corporations.yml` 쪽에서 자주 만지게 되는 것은 이 두 블록입니다.

```yaml
insolvency:
  debt-ratio-limit-percent: 400   # 부채/자본이 이걸 넘으면 관리종목
  capital-erosion-days: 3         # 자본 마이너스가 이만큼 이어지면 파산
  watchlist-price-penalty-percent: 25

state-enterprise:
  enabled: true
  shortage-threshold-percent: 40  # 장 마감 재고가 기준재고의 이 비율 미만이면 '부족'
  shortage-days: 3                # 연속 이 일수면 공기업 설립
  startup-capital: 250000         # 국고에서 나갑니다
  surplus-threshold-percent: 130  # 재고가 이 비율을 넘고
  privatise-days: 5               # 이 일수 이어지면 민영화
  max-total: 8
```

- `shortage-days` 를 낮추면 국가가 **더 자주** 끼어듭니다. 3일은 "시장의 하루 회복분
  (기준재고 쪽으로 25%)을 넘는 수요가 사흘 이어졌다" 는 뜻이라, 진짜 구조적인 부족일
  때만 걸립니다.

#### 아이템 목록 쓰는 법

`weight.tiers.*.items`, `tree-felling.logs` / `tools`, `anvil` 의 `target` 은 모두 같은 문법입니다.

```yaml
items:
  - minecraft:stone            # 낱개 ID
  - '#minecraft:planks'        # 바닐라 태그 (그 태그에 속한 전부)
  - '#myserver:custom_gear'    # 서버에 깔린 다른 데이터팩 태그
```

이 서버 버전에 없는 항목은 **경고만 남기고 건너뜁니다.** 목록 전체가 죽지 않으므로
설정 하나로 여러 버전을 커버할 수 있습니다.

#### 모루 조합법 추가하기

```yaml
anvil:
  recipes:
    my-recipe:                                        # 아무 키나 가능
      name: "&b내 조합"                                # /rpgcore recipes 표시용
      target: ['#minecraft:enchantable/sharp_weapon']  # 왼쪽 칸에 올 수 있는 것
      ingredient: minecraft:flint                      # 오른쪽 칸 재료
      ingredient-amount: 2
      repair-percent: 0                                # 최대 내구도의 N% 회복
      level-cost: 0                                    # 소모할 경험치 레벨
      enchantments:
        sharpness: 1                                   # 1회당 올릴 레벨
```

- 자주 쓰는 대상 태그: `#minecraft:enchantable/sharp_weapon`(검·도끼),
  `#minecraft:enchantable/mining`(채굴 도구), `#minecraft:enchantable/armor`(방어구),
  `#minecraft:enchantable/durability`(내구도 있는 장비 전부).
- **재료 선택 주의**: 그 장비의 바닐라 수리 재료(철 갑옷 + 철 주괴 등)를 쓰면 바닐라 수리를
  덮어씁니다. 기본 조합법이 철 '주괴' 대신 철 '블록', 숫돌을 쓰는 이유입니다.

#### 이름표 / 플레이어 목록 꾸미기

```yaml
weight:
  lore-format: "&8무게 %weight%"   # 아이템 툴팁 한 줄. ""(빈 값)이면 표시 안 함

display:
  # 조각별 서식. %party% %title% %level% %job% 이 바뀝니다.
  party-format: "&8[&d%party%&8]"
  title-format: "%title%"          # 칭호 문구는 achievements/collection.yml 에서 정합니다
  level-format: "&7Lv.&e%level%"
  job-format: "&b%job%"

  nameplate:        # 머리 위
    show-party: true
    show-title: true
    show-level: true
    show-job: true
  tablist:          # Tab 목록
    show-party: true
    show-title: true
    show-level: true
    show-job: false
```

- 파티와 칭호는 **이름 앞**, 레벨과 직업은 **이름 뒤**에 붙습니다. 사이 공백은 자동이라
  서식에 넣지 않아도 됩니다.
- 해당 정보가 없으면(파티 없음·직업 없음) 그 조각은 아예 빠집니다.
- 서식을 `""` 로 비우면 양쪽 모두에서 그 조각이 사라집니다.
- 이름표 자체를 끄려면 `settings.yml` 의 `features.nameplate`, 목록은 `features.tablist`,
  무게 툴팁은 `features.item-weight-lore` 를 `false` 로 두세요.

#### 업적 만들기 (achievements.yml)

```yaml
announce-to-server: true      # 칭호가 걸린 업적/서버 최초 업적을 전체 공지

achievements:
  my-goal:                    # 아무 키나 가능. 칭호 id 로도 쓰입니다

    description: "몬스터 100마리 처치"

    title: "&e[사냥꾼]"        # 비우면 보상만 주고 칭호는 없음
```

없는 기준을 적으면 그 업적만 건너뛰고 **쓸 수 있는 목록을 로그에 적어 줍니다.**

무엇을 '광석'과 '원목'으로 셀지는 `config.yml` 에서 바꿀 수 있습니다. 비워 두면
바닐라 기본값(광석 19종 / 원목 44종)이고, 모드나 데이터팩 블록을 세고 싶을 때만 채웁니다.

```yaml
progress:

  log-blocks: []
```

기준값은 전부 스코어보드(`rpgcore.kills` 등)에 저장되므로 `/scoreboard players get`
으로 직접 확인할 수 있고, 오프라인 플레이어의 값도 남아 있습니다.

`stats/StatType.java` 에 한 줄 추가하면 GUI 슬롯과 스코어보드 오브젝티브가 자동 생성됩니다.

단, **스탯 GUI 가 잡아 둔 칸은 6개(슬롯 10~15)** 입니다. 슬롯 16 부터는 HP·무게·포인트·
장비 칸이라 스탯이 넘어가면 겹칩니다. 7번째 스탯을 넣으면 화면에 그리지 않고 기동 로그에
경고를 남기므로, 그 전에 `gui/StatsMenu.java` 의 배치를 먼저 넓혀 주세요.

## 베드락(Geyser/Floodgate) 호환

모든 로직이 서버 사이드라 **베드락에서 별도 설정 없이 그대로 동작합니다.**
UI도 일반 상자 GUI 하나만 쓰므로 Geyser가 알아서 베드락 화면으로 번역합니다.
아이콘도 양쪽에서 동일하게 렌더되는 것만 씁니다.

유일한 차이는 **점프력 페널티**입니다. 베드락에는 플레이어 jump_strength 어트리뷰트가
없어 적용되지 않습니다. 이동속도 페널티와 허기는 그대로 걸립니다.

## 데이터 저장

플레이어 상태는 `rpgcore.*` **바닐라 스코어보드 오브젝티브**에 미러링되어 월드와 함께
저장됩니다. 별도 데이터 파일이 없고, 다른 데이터팩이나 커맨드 블록에서 읽을 수도 있습니다.

```
/scoreboard players get <player> rpgcore.level
```

접속 중인 플레이어의 값을 손으로 고치는 것은 소용이 없습니다. 플러그인은 값이 실제로
바뀔 때만 기록하므로 잠시 남아 있는 것처럼 보여도, 그 값이 다음에 바뀌는 순간과 접속을
종료할 때 덮어써집니다. 오프라인일 때 고치거나 `/rpgcore givexp` · `/rpgcore givegold` ·
`/rpgcore reset` 을 쓰세요.

**직업**만은 문자열이라 스코어보드에 담을 수 없어, 플레이어의 바닐라 playerdata 안에
저장됩니다(PersistentDataContainer). 역시 별도 파일이 생기지 않습니다.

```
/data get entity <player> data
```

**업적·칭호·도감**도 문자열이라 같은 곳(PersistentDataContainer)에 들어갑니다.
진행도 카운터(`rpgcore.kills`, `rpgcore.ores` …)와 **골드**(`rpgcore.gold`)는 정수라
스코어보드에 그대로 미러링됩니다. '서버 최초' 업적의 주인만 `records.yml` 에 남습니다.

**파티**는 이름·구성원을 가진 그룹이라 스코어보드에도 개인 데이터에도 맞지 않아,
`plugins/RPGCorePlugin/parties.yml` 에 저장됩니다. 바뀐 내용은 1초 안에 기록되므로
서버가 갑자기 내려가도 남습니다(아래 "파일이 언제 쓰이는가" 참고). 진행 중인 거래는 저장되지 않고, 서버 종료 시 물건을
주인에게 돌려준 뒤 정리됩니다.

### 파일이 언제 쓰이는가
기업·경매·파티·우편함·청사진은 **바뀔 때마다 즉시 쓰지 않고** 메모리에 모아 두었다가 기본 1초마다
한 번, **메인 스레드가 아닌 전용 스레드**에서 씁니다(`config.yml` 의 `persistence`).

실제로 재 봤을 때(2.6.6, 당시 길드 기능) 50개가 각각 54칸 보관함을 채운 상태에서 파일 한 번 쓰는 데 **65ms** —
서버 틱(50ms)보다 깁니다. 보관함을 닫을 때마다, 금고에 넣을 때마다, 전쟁이 끝날 때마다 그
비용을 그 자리에서 내고 있었습니다. 시간이 어디로 가는지 쪼개 보면 자료를 모으는 데 1ms 도
안 걸리고 **YAML 텍스트로 뽑는 데 전부** 쓰입니다. 그래서 두 작업을 갈라 놓았습니다 — 모으는
쪽은 메인 스레드(살아 있는 인벤토리를 읽어야 하므로), 뽑아서 쓰는 쪽은 별도 스레드.

한 틱 안에 500번 바뀌어도 쓰기는 한 번입니다. 네 파일이 **같은 틱에 함께** 쓰이는 것도
의도된 것입니다 — 경매 낙찰과 그 대금이 들어간 우편함은 한 거래이고, 둘을 다른 순간에 쓰면
그 사이에 크래시가 났을 때 어디에도 없는 아이템이 생깁니다.

대신 크래시 시 최대 1초어치 변경을 잃을 수 있습니다. `flush-interval-ticks` 로 조절합니다.
서버 종료 시에는 그 자리에서 동기적으로 씁니다.

기업은 `plugins/RPGCorePlugin/companies.yml` 에 저장됩니다. 명단·직급·현금·창고·공장·
**주주 명부**가 한 파일에 들어갑니다. 주주 명부는 남의 재산이므로, 읽다가 깨진 줄이 있으면
조용히 건너뛰지 않고 `SEVERE` 로 남깁니다.

청사진은 `blueprints.yml`(도면), 진행 중인 공사는 `construction.yml` 에 따로 저장됩니다.
도면은 한 번 쓰고 다시 안 쓰는 파일이고 공사는 1초마다 바뀌는 파일이라, 같이 두면 벽돌 네
장 더 쌓였다는 걸 기록하려고 5만 블록짜리 건물을 통째로 다시 쓰게 됩니다.

**예전 길드 데이터는 한 번만, 자동으로 기업이 됩니다.** `guilds.yml` 이 있으면 첫 기동에
길드 하나가 회사 하나로 바뀝니다 — 길드장이 대표, 길드원이 직원, 금고와 영지 투자액이
자본금. 보관함 물건은 **길드장 우편함으로 반환**됩니다(회사 창고는 품목별 개수만 세므로
인챈트나 이름이 붙은 물건을 담을 수 없습니다). 변환된 회사를 **디스크에 쓴 다음에야**
`guilds.yml` 이 `guilds.yml.migrated` 로 이름이 바뀌므로, 그 사이에 서버가 죽어도 길드가
사라지지 않고 다음 기동에 다시 변환됩니다.

경매 진행 상황은 `plugins/RPGCorePlugin/auctions.yml`, 아직 전달하지 못한 물건과 골드는
`plugins/RPGCorePlugin/mailbox.yml` 에 저장됩니다. 이 파일들이 존재하는 이유가 "서버가
곱게 안 내려간 경우"이므로 종료만 믿지 않고 **바뀐 뒤 1초 안에** 기록합니다.

경매에 올라간 물건과 최고 입찰 골드는 각각 판매자와 입찰자에게서 실제로 빼 온 것이므로,
`auctions.yml` 은 캐시가 아니라 남의 재산 보관 장부입니다. 읽다가 깨진 항목이 있으면
조용히 건너뛰지 않고 `SEVERE` 로 남깁니다.

시장·은행·중앙은행은 각자 자기 파일을 씁니다. 셋 다 **설정이 아니라 상태**이고, 위의 네
파일과 같은 라운드에 같은 스레드에서 쓰입니다.

| 파일 | 담는 것 |
|---|---|
| `market.yml` | 품목별 재고·**장 마감 재고**·심리·가격·전일 종가·누적 거래량·24일치 가격 이력, 비축 물자, 시장 금고, 물가 수준, 최근 시황 |
| `bank.yml` | 계좌별 입출금·정기예금·대출·**국채**·신용점수와 그 이력, 법인계좌 표시와 신고자산, 은행 금고 현금·중앙은행 차입·구제금융·상각 누계 |
| `macro.yml` | 경제일, 정책금리, CPI 와 그 이력, 물가상승률, 잠재 GDP, **주가지수 기준값과 이력**, 발권·수수료 누계, 금리 결정 이력 |
| `companies.yml` | 등기부(현금·창고·공장·주주명부·정책), **공기업 여부·관리종목 여부·자본잠식 일수·전일 법인세**, 품목별 **부족/과잉 연속일수** |

**예금은 남의 돈입니다.** 플레이어 지갑에서 실제로 빠져나온 골드이고 다른 어디에도 없으므로,
입금·출금·대출·상환은 경매 입찰과 똑같이 **그 자리에서 디스크에 씁니다.** 지갑 쪽은 바닐라
스코어보드(월드와 함께 저장)에 있어서 두 쪽을 한 트랜잭션으로 묶을 수는 없지만, 이쪽을 즉시
쓰면 어긋날 수 있는 창이 분 단위에서 밀리초 단위로 줄어듭니다.

반대로 시장 재고는 **1초짜리 일괄 쓰기에 맡깁니다.** 재고는 남의 재산이 아니라 값을 정하는
숫자이고, 크래시로 1초어치 채굴량이 사라져도 창고 하나에 몇 개 차이일 뿐이기 때문입니다.

어트리뷰트 모디파이어 네임스페이스는 플러그인 이름에서 나오므로 `rpgcoreplugin:*` 입니다.

```
/attribute <player> minecraft:movement_speed modifier value get rpgcoreplugin:weight_speed
```

### 2.2.0 검증

`/menu` 와 경매장을 추가한 뒤 같은 방식으로 확인했습니다 — Paper 26.2 실서버 기동·리로드·
종료 예외 0건, 검사 항목 43개 전부 통과.

경매의 **정산 경로는 실제 코드로 돌려 봤습니다.** 경매 장부(`auctions.yml`)는 서버가 쓰는
그 파일이라, 만료된 물건을 직접 써 넣고 만료 틱을 돌리면 실제 낙찰/유찰 처리가 그대로
실행됩니다.

- 유찰: 물건이 판매자 우편함으로, 개수와 NBT 까지 그대로
- 낙찰: 물건은 낙찰자에게, 대금은 판매자에게 수수료 5%를 뗀 950 (1000 입찰 기준).
  **떼인 50 + 받은 950 = 1000** — 입찰 시점에 이미 걷어 간 금액과 정확히 일치하므로
  골드가 생기지도 사라지지도 않습니다
- 만료 캐시(매 틱 장부를 훑지 않고 "가장 빠른 종료 시각"만 비교)를 넣은 뒤에도 만료된
  물건은 닫히고, 아직 남은 물건은 열린 채 유지되며, 그 판매자에게 대금이 먼저 가지 않음
- 입찰 사다리가 1골드 물건에서도 올라감 (퍼센트 증분이 0으로 내림되지 않음)
- 우편함: 인챈트된 아이템과 골드가 재시작(파일 재적재) 후에도 그대로

사람이 직접 해 봐야 하는 것 (경매): `/auction sell` 과 GUI 에서의 입찰·즉시구매·내리기.
이 경로들은 살아 있는 Player 객체가 필요해 무인 검증으로는 닿지 못했습니다.
특히 **두 사람이 같은 틱에 같은 물건을 즉시구매**하는 경우 — 코드상으로는
`AuctionListing.settle()` 이 한 번만 성공하고 모든 종료 경로가 그것을 먼저 통과하므로
한 명만 사고 다른 한 명은 "방금 다른 사람이 가져갔습니다" 를 받지만, 실제로 눌러 본 것은
아닙니다.

### 길드·영지 검증

길드도 같은 방식으로 확인했습니다. `guilds.yml` 이 서버가 쓰는 그 파일이라, 길드를 직접
써 넣고 불러오면 실제 영지 등록·보관함 복원·보호 판정 코드가 그대로 돕니다.
검사 항목은 총 **68개, 전부 통과**했고 기동·리로드·종료 예외 0건입니다.

- 영지 판정: 중심 / 경계 / 경계 바로 밖 / 대각선 모서리 밖 / 음수 좌표 경계 / 아주 먼 곳.
  깃발 위치는 좌표가 정확히 일치할 때만 깃발로 인정 (한 칸 위는 아님)
- **청크 색인이 중심 청크 밖에서도 답한다** — 매 틱이 아니라 매 블록 파괴마다 도는
  조회라 색인이 틀리면 보호가 통째로 새거나 서버가 느려집니다
- 보관함: 설정한 크기로 복원되고, 넣어 둔 칸 번호 그대로, 개수와 인챈트까지 동일.
  빈 칸은 빈 칸. **두 번 열어도 같은 컨테이너 객체** (사본이 아님)
- 영지 간격: 필요한 간격 안쪽이면 충돌로 판정, 바깥이면 아님, 다른 월드끼리는 충돌 없음
- 명단: UUID 로 길드원과 외부인을 구분, 어느 구성원에게서든 같은 길드를 찾아냄

사람이 직접 해 봐야 하는 것 (길드): 깃발을 실제로 세우고 부수는 것, 외부인이 블록을 캘 때
정말 막히는지, 버프가 화면에 뜨는지, 작물이 빨라지는지. 모두 살아 있는 Player 나 월드
상호작용이 필요해 무인 검증으로는 닿지 못했습니다.

  호출되므로 100명이면 초당 400개의 일회용 배열이 상수 두 개 때문에 생기고 있었습니다.
- **깃발 순찰 검사**: 영지 하나를 보려고 매번 전체 영지 목록을 새 리스트로 만들고 있었습니다.
  기능을 켜 두기만 해도 드는 비용이 길드 수에 비례했습니다.
- **순위표**: 항목마다 오브젝티브를 이름으로 다시 찾고 있었습니다. 한 번만 찾도록 바꿨습니다.
- **우편함 수령**: 골드 항목마다 잔액을 스코어보드에 기록했습니다. 합산 후 한 번만 기록합니다.

고친 버그:

- **길드 초대가 접속 종료 시 정리되지 않았습니다.** 파티·대결·거래는 모두 정리하는데 길드만
  빠져 있었고, 만료 처리는 대상이 `/guild accept` 를 쳐야만 돌았습니다 — 로그아웃한 사람이
  절대 하지 않는 바로 그 행동입니다.
- **작물 성장 처리가 이벤트 상태를 두 번 읽고 있었습니다.** `getBlockData()` 는 사본을
  주므로, 사본을 받아 온 그 상태 객체에 다시 써야 합니다. 한 번만 잡도록 고쳤습니다.
- **`flushNow()` 가 쓰기 스레드와 같은 파일을 동시에 쓸 수 있었습니다** (제가 이번에 넣은
  버그입니다). 두 스레드가 한 파일을 쓰면 둘 중 오래된 쪽이 남는 게 아니라 **아무것도 안
  남습니다.** 쓰기 구간에 잠금을 걸고, 종료 쓰기 이후에는 대기 중이던 쓰기를 버립니다.
- **Bukkit 비동기 스케줄러로는 안 됐습니다** (역시 이번에 넣은 버그). 그 스케줄러는 메인
  스레드 하트비트에서 작업을 꺼내므로, 메인 스레드가 바쁘거나 멈춰 있거나 내려가는 중이면
  — 즉 백그라운드 쓰기가 가장 필요한 순간에 — 쓰기가 시작되지 않습니다. 검증에서 5초를
  기다려도 파일이 안 생겨 발견했고, 전용 스레드로 바꿨습니다.

### 길드전·투자 검증

전쟁과 금고도 같은 방식으로 실제 코드를 돌렸습니다. 검사 항목 총 **97개, 전부 통과**,
기동·리로드·종료 예외 0건 · SEVERE 0건.

- **전쟁 단계**: 선포 직후는 준비 중(교전 아님), 준비 시간이 지나면 교전, 종료 시각이
  지나면 끝. 양쪽 어디서 조회해도 같은 전쟁을 찾아냄
- **폭발 보호가 단계를 따라감**: 준비 중에는 영지가 여전히 보호되고, 교전이 시작되면
  풀리며, 전쟁이 끝나면 다시 걸림
- **전리품 계산**: 금고 500 vs 8,000 에서 승자 8,500 / 패자 0. 두 금고의 합이 전후로
  동일 — 전쟁으로 골드가 생기지도 사라지지도 않음. 승부는 한 번만 확정되고 재대결은
  대기시간에 막힘
- **투자 사다리**: 미투자는 기본 반경, 1블록 값에서 1 모자라면 안 넓어지고 남은 금액이
  정확히 1, 3블록 값이면 +3, 한계를 넘겨 투자해도 최대에서 멈추고 더 팔 것이 없음
- **넓어진 영지가 실제로 보호됨**: 투자 후 청크 색인이 새 바깥 테두리까지 답하고, 그
  한 블록 밖에서는 답하지 않음 (색인을 갱신하지 않았다면 돈 주고 산 땅이 무방비)
- **깃발 간격이 성장을 막지 않음**: 최대 반경 기준(208블록)으로 자리를 잡으므로 두 영지가
  모두 최대까지 커져도 겹치지 않음

지속성 계층을 통째로 바꿨으므로 검사도 늘렸습니다 — 총 **109개 전부 통과**. `save()` 만으로는
디스크를 건드리지 않고, 플러시하면 쓰이며, 인챈트된 아이템이 보관함 칸 번호·개수까지 그대로
돌아오고, 우편함 항목도 비동기 쓰기를 건너 살아남는 것을 확인했습니다.

사람이 직접 해 봐야 하는 것 (전쟁): `/guild war` 로 선포한 뒤 실제로 상대 깃발을 부숴
승리 처리가 도는지, 교전 중에 상대 영지 블록이 정말 캐지는지. 블록 파괴 이벤트와 살아
있는 Player 가 필요한 부분입니다.

### 2.5.0 — 콘텐츠 확장과 밸런스 검증

콘텐츠를 대량으로 넣으면 **설정 파일이 조용히 반쯤만 읽히는 것**이 가장 흔한 사고입니다.
이름이 틀린 아이템 하나가 경고 한 줄만 남기고 넘어가면, 다 모을 수 없는 도감이

```
[RPGCorePlugin] Weight table loaded: 280 materials
[RPGCorePlugin] Anvil recipes loaded: 16.
[RPGCorePlugin] Jobs loaded: 15.
[RPGCorePlugin] Achievements loaded: 41.
[RPGCorePlugin] Collection log loaded: 20 categories, 363 entries.
[RPGCoreVerify] ===== RPGCORE VERIFY: 114/114 passed =====
```

실제로 서버가 잡아낸 것들 — 전부 **추측으로는 찾지 못했을** 것들입니다.

- `#minecraft:corals` · `#minecraft:coral_blocks` · `#minecraft:base_stone_overworld` 는

  는 **이 버전에 아예 없는 이름**이었습니다 → 디스크 21종을 낱개로, 모루 조합법은
  `#minecraft:swords` 로 교체

  추가되면서 이름이 갈라진 것으로, 바닐라 지식으로는 틀린 줄 알 수 없습니다
- `crimson_stem` · `warped_stem` 은 `#minecraft:logs` 에 들어 있어 원목 분류와 겹쳤습니다
  → 네더 분류에서 빼고 네더 전용 블록으로 교체 (한 아이템은 한 분류에만 들어갑니다)

밸런스 쪽은 수치를 고친 뒤 **기존 114개 검사를 그대로 다시 돌려** 스탯·지속성·전쟁·경매
동작이 깨지지 않았음을 확인했습니다.

사람이 직접 해 봐야 하는 것: 소프트캡을 넘긴 스탯이 `/stats` 창에 실제로 어떻게 보이는지,
LUCK 2배 보상 액션바가 뜨는지, 3단계 직업의 체력 페널티가 하트 칸으로 체감되는지.
화면과 살아 있는 Player 가 필요한 부분입니다.

### 2.6.0 — Discord 연동 검증

남의 서버로 HTTP 를 보내는 코드는 **읽어서 맞는지 알 수 없습니다.** 그래서 디스코드
웹후크 흉내를 내는 작은 수신 서버를 띄우고 실제 소켓에 대고 돌렸습니다 — 검사 **22개
추가, 총 136개 전부 통과**.

실제로 잡힌 요청 기록입니다.

```
[webhook]   embeds=1   mentions_off=True  ['🟢  서버가 열렸습니다']
[webhook]   embeds=1   mentions_off=True  ['💀  "quoted" \backslash\ 한글 @everyone']
[webhook]   embeds=10  mentions_off=True  ['batched 0' ... 'batched 9']
[ratelimit] embeds=1   mentions_off=True  ['rate limited']      <- 429
[ratelimit] embeds=1   mentions_off=True  ['rate limited']      <- 재전송, 성공
[gone]      embeds=3   mentions_off=True  ['to a deleted webhook 0' ...]
[webhook]   embeds=1   mentions_off=True  ['🔴  서버가 닫혔습니다']
```

- **종료 알림이 실제로 도착합니다.** 전송 스레드가 데몬이라, 큐에 넣기만 하면 JVM 이
  먼저 끝나 아무도 못 봅니다. 마지막 줄이 그게 아님을 보여줍니다
- **10개가 1개 요청**으로 나갔습니다 (`batched 10 events into 1 request(s)`)
- **429 는 기다렸다가 재전송**, **404 는 3건을 1요청으로 시도하고 재시도 없음**
- **디스코드가 죽어 있어도 막지 않습니다**: 응답 없는 주소로 2,000건을 쌓는 데 **5ms**
- 따옴표·역슬래시·제어문자·한글·`@everyone` 이 섞인 메시지를 **진짜 JSON 파서가
  받아들였고**, `allowed_mentions` 가 모든 메시지에서 비어 있었습니다

주소가 새지 않는지는 별도로 확인했습니다 — 웹후크에 눈에 띄는 가짜 토큰을 넣고 기동 ·
`/rpgcore check` · `/rpgcore reload` 를 돌린 뒤 콘솔 전체를 뒤져 **0건**.

사람이 직접 해 봐야 하는 것: 실제 디스코드 채널에서 색 막대와 머리 아이콘이 의도대로
보이는지, 그리고 접속·사망·레벨업·업적 알림의 문장이 실제 플레이어 이름으로 어떻게
읽히는지. 살아 있는 Player 와 진짜 웹후크가 필요한 부분입니다.

### 2.6.1 — 전수 점검

전체 코드를 다시 훑고, 읽어서 판단하는 대신 **테스트를 세워 확인**했습니다.
검사 **164개 전부 통과** (28개 추가).

**진짜 버그 세 개**

- **전쟁 중 폭발로 깃발을 부수면 아무 일도 일어나지 않았습니다.** 전쟁 중에는 폭발
  보호를 일부러 풀어두므로 TNT 는 깃발을 치는 가장 자연스러운 수단인데, 폭발로
  깃발이 사라지면 **블록만 없어지고 영지는 그대로 남고 전쟁도 끝나지 않았습니다.**
  깃발 없는 영지가 계속 보호받고 버프까지 주는 상태였습니다. 이제 폭발로 무너진
  깃발도 영지를 끝내고, 전쟁 중이었다면 상대 길드의 승리로 정산됩니다
- **Discord 가 계속 429(속도 제한)를 주면 전송 스레드가 영영 멈췄습니다.** 재시도
  횟수를 깎지 않고 무한히 기다리는 구조여서, 디스코드 장애 한 번이면 그 뒤의 모든
  알림이 영원히 밀립니다. 대기 횟수에 상한(5회)을 두었습니다
- **누적 카운터가 21억을 넘으면 0으로 초기화**되었습니다. 음수로 뒤집힌 값을
  `Math.max(0, ...)` 가 0으로 깎기 때문입니다. 골드와 같은 방식으로 상한에서 멈추게
  했습니다

**품질**

- `gui.size` 를 **설정을 읽는 자리에서** 합법적인 상자 크기로 맞춥니다. 예전에는 창을
  여는 쪽에서 맞췄는데, 새 화면을 추가하는 사람이 빠뜨리면 명령어가 예외로 죽습니다
- Discord 의 `HttpClient` 를 전송 스레드에서 만듭니다. 예전에는 첫 알림이 발생한
  스레드(대개 메인)에서 셀렉터 스레드까지 만들었습니다

**설정 퍼즈 검사 (신규)**

운영자가 실제로 서버를 깨뜨리는 방식은 설정 파일에 이상한 값을 넣는 것입니다.
모든 숫자 설정에 **0 / 음수 / `Integer.MAX_VALUE` / 아예 다른 타입**을 넣고 다시
불러온 뒤, XP 곡선·스탯 곡선·상자 크기를 실제로 호출했습니다 — **네 경우 모두 예외
없음**, 곡선은 120레벨까지 양수 유지, 창 크기는 항상 합법.

**성능은 측정했고, 고칠 것이 없었습니다**

| 측정 | 결과 |
|---|---|
| 스코어보드 미러 비교 1회 | **0.74 µs** (블록 하나 캐면 3회 ≈ 2 µs) |
| Discord 임베드 생성 1개 | **1.9 µs** (메인 스레드가 내는 유일한 비용) |
| `claimAt()` 1회 | **214 ns** |
| 길드 50개 플러시 (메인 스레드 몫) | **1.03 ms** |

블록 채굴 경로가 의심스러워 재봤지만, 100명이 초당 20블록씩 캐도 **초당 4.4ms**
(코어 하나의 0.4%)입니다. 고칠 만한 것이 없어서 **고치지 않았습니다.**

**테스트가 실제로 버그를 잡는지도 확인했습니다**: 깃발 수정을 일부러 되돌리고 돌려
**2건이 실패**하는 것을 본 뒤 복구했습니다. 통과하는 것만으로는 검사가 살아 있다는
증거가 되지 않습니다.

### 2.6.2 — 전체 정독

16,800줄을 처음부터 끝까지 읽었습니다. 앞선 점검이 grep 과 표본 확인이었다면 이번에는
전수 확인입니다. 검사 **174개 전부 통과** (10개 추가).

**먼저, 지난번 보고를 하나 정정합니다.** 2.6.1 에서 "경매 마감 뒤 캐시 갱신"을 버그
수정으로 올렸는데, **버그가 아니었습니다** — 바로 다음 줄의 `save()` 가 이미 같은 일을
하고 있었습니다. grep 결과만 보고 호출 위치를 확인하지 않은 제 잘못입니다. 중복 호출은
지웠고, README 에서도 항목을 뺐습니다.

**새로 찾은 진짜 결함 넷**

- **이름을 바꾸면 다른 플러그인의 스코어보드 데이터가 지워졌습니다.** 이름 변경 시
  `resetScores(옛이름)` 을 불렀는데, 이건 **서버의 모든 목표에서** 그 이름을 지웁니다 —
  다른 플러그인과 데이터팩의 것까지. 남의 데이터를 조용히 삭제하고 있었습니다.
  이제 RPGCore 가 자기 목표만 하나씩 지웁니다
- **우편함이 가득 차면 아이템을 말없이 삭제했습니다.** 상한이 200개인데, **입찰에서
  밀릴 때마다 1칸**씩 쌓입니다. 경매를 활발히 하는 플레이어는 평범하게 도달합니다.
  검증에서 환불 300건을 넣자 **100건이 실제로 사라졌습니다.** 골드는 같은 사유끼리
  합치도록 바꿔 상한에 닿지 않게 했습니다 (300건 → 1칸, 2,100골드 보존)
- **우편함 골드 합계가 int 였습니다.** 넘치면 음수가 되고, 음수는 지급이 무시되는데
  항목은 이미 지워진 뒤라 **전액 증발**합니다. long 으로 합산하고 상한에서 멈춥니다
- **레벨업 루프에 상한이 없었습니다.** `xp-base: 1`, `xp-growth: 0` 은 허용되는
  설정이고(둘 다 클램프를 통과합니다) 그러면 레벨당 1 XP 입니다. 여기에 큰 XP 를 한 번
  주면 루프가 수십억 번 돌며 매번 `Math.pow` 를 호출합니다 — **메인 스레드가 그동안
  멈춥니다.** 한 번에 1,000레벨까지만 올리고 나머지는 적립합니다

**작은 것들**

- 크리에이티브에서 몬스터를 잡아도 XP·골드·업적이 들어왔습니다. 블록 채굴과 낚시는
  크리에이티브를 제외하는데 처치만 빠져 있었습니다 — 운영자가 자기에게 공짜로 줄 수
  있는 유일한 진행이었습니다
- 행운 2배가 `보상 * 2` 였습니다. 보상에 상한이 없어 큰 값이면 음수가 되고, 음수는
  모든 지급 경로가 무시합니다 — **터진 쪽이 오히려 0을 받았습니다**
- 영지 수 카운터가 실제로 지운 게 없어도 감소했습니다. 깃발 파괴·폭발·해체·순회 점검
  네 경로가 같은 영지에 닿으면 음수로 내려갑니다

**읽었지만 고치지 않은 것도 있습니다.** 거래 취소 시 인벤토리가 가득 차면 발밑에
떨어뜨리는데, 처음엔 우편함으로 보내야 하는 버그로 봤습니다. 확인해 보니 대결도 같은
방식이고, 오프라인 플레이어는 이미 우편함으로 갑니다 — 의도된 관용구라 그대로 두었습니다.

**여섯 개 검사가 실제로 잡는지 확인했습니다**: 수정을 전부 되돌리고 돌려 **6건 실패**,
복구 후 174건 통과. 특히 "2,100골드 중 한 닢도 잃지 않는다" 가 되돌린 코드에서 실패한
것이 우편함 상한이 진짜로 값을 파괴하고 있었다는 증거입니다.

**테스트로 확인할 수 없는 것**: 레벨 루프 상한과 크리에이티브 제외, 행운 오버플로는
살아 있는 Player 가 필요해 코드로만 확인했습니다.

### 2.6.3 — 봇으로 실제 플레이 확인

지난 몇 차례 "살아 있는 Player 가 필요해 확인 못 함"으로 남겨둔 항목들을, **실제
마인크래프트 클라이언트를 붙여서** 확인했습니다. 봇 검사 **27개 전부 통과**, 서버 내부
검사 174개도 그대로 통과.

**붙이는 데 걸린 것**

이 서버는 26.2(프로토콜 776)인데 `minecraft-data` 의 패킷 정의는 **26.1(775)까지**만
있습니다. 26.1 의 패킷 레이아웃을 빌려 쓰되 핸드셰이크에는 776 을 알리도록 데이터셋을
등록했습니다. 패킷이 실제로 바뀌었다면 디코드 단계에서 시끄럽게 실패하므로, 조용히
엉뚱한 걸 검사하게 되지는 않습니다.

실제로 두 가지가 어긋났고, 둘 다 **클라이언트 쪽 한계**입니다(서버 결함 아님):

- `teams` 패킷(이름표)이 26.2 에서 바뀌어 디코드에 실패하고, 그게 패킷 스트림을
  어긋나게 해 연결이 끊깁니다 → **봇 실행 동안에는 이름표/Tab 표시를 껐습니다.**
  즉 **이름표는 이 봇으로 검증하지 못했습니다**
- 엔티티 타입 ID 가 밀려서 좀비가 `zombie_horse` 로 보입니다 → 이름 대신 **거리로**
  가장 가까운 몹을 때리게 했습니다

**확인한 것**

| 항목 | 결과 |
|---|---|
| 첫 접속 환영 메시지 · `/stats` 안내 | 실제로 도착 |
| `/stats` 창 | 27칸(합법 크기), 5개 스탯 전부 |
| **소프트캡 설명이 타일에 보임** | 보임 |
| **LUCK 의 "처치 보상 2배" 표기** | 보임 |
| 레벨업 메시지 · 남은 포인트 | 도착 |
| **Discord 레벨 중계 게이트** | **정확히 [10, 15, 20, 25, 30]** — 하한 10, 5의 배수 |
| **생존 모드 처치** | 처치수 0 → 1, 골드 0 → 6 |
| **크리에이티브 처치** | 처치수 1 → 1, 골드 6 → 6 (안 셈) |
| **레벨 루프 상한** | 20억 XP 에 0.5초 만에 응답, 경고 로그, 레벨 3001 |

| 접속/퇴장 → Discord | 도착 |

크리에이티브 검사가 의미를 가지려면 **생존 모드에서는 실제로 올라간다는 대조군**이
필요합니다. 처음 두 번의 실행에서는 몹이 아예 죽지 않아 양쪽 다 "변화 없음"으로
**거짓 통과**했고, 그걸 알아채고 봇이 진짜로 때려서 죽이도록 고친 뒤에야 대조가
성립했습니다.

레벨 3001 은 상한이 **`addXp` 호출 단위**라서 그렇습니다. 업적 보상 XP 가 `addXp` 를
다시 부르므로 한 명령이 1,000레벨짜리 라운드를 몇 번 쌓습니다(`Stopped after` 가 3번
찍혔습니다). 무한히 도는 것은 아니고 — 업적은 한 번씩만 지급되므로 — 20억이 아니라
3천에서 멈춥니다.

### 2.6.4 — 남은 것 전부 봇으로 확인, 레벨 상한 수정

봇 검사를 **28 + 25 + 3 = 56개**로 늘리고, 서버 내부 174개와 합쳐 **230개 전부 통과**.

**고친 것: 레벨 상한이 실제로는 상한이 아니었습니다**

2.6.3 에서 "1,000레벨에서 멈춘다"고 했는데 실제로는 **3,001레벨**이 나왔습니다. 상한이
`addXp` **호출 단위**였고, 업적 보상 XP 가 `addXp` 를 다시 부르기 때문입니다. 즉 경고는
"멈췄다"고 찍으면서 실제로는 2,000레벨을 더 줬습니다 — **로그가 거짓말을 하고 있었습니다.**

한 번의 지급 전체가 상한을 공유하도록 고쳤고, 두 가지를 더 바로잡았습니다:

- 레벨을 **주기 전에** 상한을 확인합니다 (뒤에서 확인하면 중첩 라운드마다 한 레벨씩 샙니다)
- 경고는 **한 번만** 찍습니다

결과: **레벨 1001, 경고 1회** — 이제 로그와 동작이 일치합니다.

**남아 있던 이름표 검증**

이름표는 스코어보드 팀이라 이 클라이언트가 디코드하지 못하고, 그 패킷이 날아다니는
동안에는 **두 번째 클라이언트가 로그인조차 못 합니다.** 그래서 봇 하나로 붙이고 서버에
직접 물었습니다 — 팀이 생겼는지, 그리고 코드 주석이 걱정하던 대로 **나간 뒤에 치워지는지**.

```
There are 1 team(s): [Np53307]
Team [Np53307] has 1 member(s): Np53307
-- 퇴장 후 --
There are no teams
```

**두 번째 봇 판: 손 안 댔던 시스템들** (봇 2개)

| 항목 | 결과 |
|---|---|
| 플레이어 목록에 RPG 정보 | `Ga… Lv.1` |
| 소지 무게 | 0 → 5120 (한도 100), 등급 3, 비우면 복귀 |
| 직업 선택 | 창 18칸, 1단계 제공 / 3단계 잠김, **전사의 VIT+2 가 체력 21 → 25 로** |
| 도감 | `[도감] Diamond 등록! (광물 1/12)` |
| **길드 영지 보호** | **외부인이 캔 블록은 그대로 남고, 주인이 캔 블록은 사라짐** |
| 경매 | 등록 + 수수료, 상대 플레이어 창에 가격표와 함께 보임 |
| 연쇄 벌목 | 한 번 캐서 **원목 5개** |

**제 검사가 틀린 걸 네 번 잡았습니다** (모두 플러그인 결함 아님):

1. **봇 둘 다 op 를 줬습니다.** `mayBuild()` 는 `rpgcore.admin` 을 통과시키고, Bukkit 은
   등록되지 않은 권한을 **운영자에게 기본 허용**합니다. 그래서 "외부인이 블록을 부쉈다"는
   결과가 나왔는데, 사실은 그 외부인이 운영자였습니다
2. **클라이언트가 보고한 채굴 성공은 증거가 아닙니다.** 서버가 취소해도 클라이언트는
   자기 기준으로 "끝났다"고 합니다. 블록이 **실제로 남아 있는지** 서버에 물어야 합니다
3. 좌표 오프셋에 `|| -1` 을 써서 **0 이 falsy 로 걸렸습니다** — 바닥 대신 기반암을 팠습니다
4. 26.1 패킷 표로 26.2 를 읽으니 **아이템·엔티티·블록 ID 가 밀립니다** (좀비가
   `zombie_horse`, 깃발이 `shield`). 이름 대신 **표시 이름과 서버 상태**로 확인합니다

세 번은 **거짓 통과**였습니다 — 통과했지만 아무것도 증명하지 못한 상태였고, 그걸
알아채고 고친 뒤에야 결과가 의미를 가졌습니다.

### 2.6.5 — 쓰다가 죽으면 무엇이 남는가

이번에는 "코드를 읽어서 틀린 곳 찾기"를 멈추고 **다른 각도**로 봤습니다. 논리는 맞는데
**중간에 죽으면 디스크에 무엇이 남아 있는가**. 여기서 결함 세 개가 나왔고, 그중 하나는
**이번에 제가 직접 넣은 것**이었습니다.

**1. 파일이 반쯤 쓰인 채로 남을 수 있었습니다**

Bukkit 의 `FileConfiguration.save(File)` 는 `FileOutputStream` 을 여는데, 그건 **한 바이트도
쓰기 전에 대상 파일을 0바이트로 잘라냅니다.** 그 사이에 프로세스가 멈추면 다음 부팅 때
읽히는 게 그 잘린 파일입니다. 그리고 그 파일에 들어 있는 건 **길드 금고, 경매 예치물,
우편함** — 전부 남의 물건입니다.

이론이 아니라는 걸 재보려고, 파일을 다시 쓰는 동안 다른 스레드가 크기를 계속 읽게 했습니다.

| | 잘린 상태로 관측 | 표본 |
|---|---|---|
| Bukkit 방식 (대조군) | **37,402회** | 4,416,792 |
| `AtomicYaml` | **0회** | 2,527,141 |

임시 파일에 쓰고 → `fsync` → **`ATOMIC_MOVE`** 로 덮습니다. 읽는 쪽은 옛 파일 전체이거나
새 파일 전체이지, 어느 쪽의 조각도 아닙니다. 쓰다가 실패하면 **원본은 손도 대지 않은 채**
남습니다.

값이 궁금할 테니 재봤습니다. Bukkit 도 어차피 **먼저 전체를 문자열로 만든 다음** 파일을
열기 때문에, 직렬화 비용은 양쪽이 같습니다. 차이는 임시 파일 + `fsync` + 이름 바꾸기뿐입니다.

| 파일 | 크기 | Bukkit | AtomicYaml | 차이 |
|---|---|---|---|---|
| 길드 50개, 금고 가득 | 433,557 B | 38.2 ms | 44.8 ms | **+6.5 ms** |
| 길드 5개, 금고 가득 | 43,372 B | 3.6 ms | 4.4 ms | **+0.8 ms** |
| 길드 50개, 금고 빔 | 1,507 B | 0.3 ms | 0.6 ms | **+0.4 ms** |

**2. 아이템이 두 곳에 동시에 존재했습니다 (실제로 재현)**

인벤토리는 바닐라가, 경매 물품은 이 플러그인이 씁니다. **주기가 다릅니다** — 바닐라는
자동 저장 타이머(분 단위), 플러그인은 1초 안쪽. 그 사이가 통째로 창입니다.

봇에게 다이아몬드 검을 주고 → `save-all` → 경매 등록 → 플러그인 저장 대기 → **`SIGKILL`**.
재시작 후:

```
carrying=True   listed=True      ← 검이 두 개가 됐습니다
```

`HandOver` 로 양쪽을 **함께** 내보내되, **물건을 내주는 쪽을 먼저** 씁니다. 그래야 남은
틈에서 죽었을 때 복제가 아니라 **소실**이 됩니다. 이건 일부러 고른 방향입니다 — 없어진
아이템은 문의가 한 건 오지만, **복제된 아이템은 아무도 신고하지 않고 경제만 조용히
망가집니다.**

```
carrying=False  listed=True      ← 4/4 통과
```

**3. 그 고침 자체가 틀려 있었습니다**

위를 고쳐놓고 다시 읽다가 알아챘습니다. 비동기 기록기는 **잠금을 잡기 전에** 대기 슬롯에서
스냅샷을 꺼냅니다. 그 사이에 `flushBlocking()` 이 끼어들면 — 새 상태를 쓰고, 잠금을 놓고,
그 다음에 **기록기가 옛 스냅샷을 그 위에 덮습니다.**

이게 왜 치명적이냐면, **죽지 않아도 아이템이 사라집니다.** 플레이어 인벤토리는 검 없이
저장됐는데, 경매 파일이 등록 이전으로 되돌아가면 검은 어디에도 없습니다.

그 교차를 4,000번 강제하고 파일이 **뒤로 가는지** 지켜봤습니다.

| | 뒤로 감 | 최대 되감김 |
|---|---|---|
| 고치기 전 | **1,328회** | 3 버전 |
| 고친 뒤 | **0회** | — |

스냅샷마다 **번호**를 붙이고, 이미 디스크에 있는 것보다 오래된 스냅샷은 **쓰지 않고
버립니다.** 파일은 앞으로만 갑니다.

**남아 있는 한계** — 2.6.6 에서 해결했습니다. 아래를 보세요.

길드 금고 한 세션은 **양방향**입니다 — 넣기도 하고 빼기도 합니다. 넣는 쪽은 "플레이어
먼저", 빼는 쪽은 "금고 먼저"가 안전한데, 두 개를 한 번씩만 쓰는 한 **둘 다 만족시키는 순서는
없습니다.** 당시에는 "플레이어 먼저"라서, 같은 세션에서 **꺼낸** 물건에 복제 창이
남았습니다.

**검사**: 서버 내부 **182개**(8개 추가), 봇 28 + 25 + 3, 크래시 4 — **242개 전부 통과**.

### 2.6.6 — 양방향 금고를 닫고, 파일끼리의 순서를 바로잡음

2.6.5 에서 "2단계 커밋이 필요해서 범위 밖"이라고 적어둔 것을 해결했고, 같은 잣대를
**파일과 파일 사이**에 대봤더니 하나가 더 나왔습니다.

**1. 양방향 금고 세션 (2.6.5 의 미해결 항목)**

한 번씩만 쓰는 한 순서로는 못 푼다고 했는데, 그건 맞습니다. **세 번** 쓰면 풀립니다.
가운데에 **어느 쪽 물건도 주장하지 않는 상태**를 한 번 끼워 넣으면 됩니다.

| 쓰기 | 금고 파일 | 플레이어 파일 | 넣은 물건 | 꺼낸 물건 |
|---|---|---|---|---|
| (이전) | 꺼낸 것 있음 | 넣은 것 있음 | 플레이어 | 금고 |
| 1. 바닥 | 둘 다 없음 | 넣은 것 있음 | 플레이어 | **아무도 없음** |
| 2. 플레이어 | 둘 다 없음 | 꺼낸 것 있음 | **아무도 없음** | 플레이어 |
| 3. 금고 | 넣은 것 있음 | 꺼낸 것 있음 | 금고 | 플레이어 |

어느 줄에서 죽어도 **두 곳에 동시에 있는 칸이 없습니다.** 여기서 "바닥"은 빈 금고가
**아닙니다** — 그러면 아무도 안 건드린 물건까지 같은 공중에 떠서, 그 순간 죽으면 **길드 금고가
통째로 비워집니다.** 바닥은 *열었을 때 있던 것* 과 *지금 있는 것* 의 **품목별 최솟값**, 즉
"이번 세션이 건드리지 않은 전부"입니다.

한쪽으로만 간 세션은 이 값을 **치르지 않습니다** — 예전처럼 두 번만 씁니다.

검사는 통과 여부가 아니라 **불변식**을 봅니다. 크래시가 멈출 수 있는 네 순간마다, 두 파일이
합쳐서 실제 개수보다 많이 주장하는지:

```
crash here -> D 5/5  G 2/2  I 3/3
crash here -> D 5/5  G 0/2  I 3/3     ← 금괴 2개가 잠시 사라짐 (안전한 방향)
crash here -> D 5/5  G 2/2  I 0/3     ← 철괴 3개가 잠시 사라짐
crash here -> D 5/5  G 2/2  I 3/3
```

산수는 맞아도 **살아 있는 인벤토리를 바꿨다가 되돌리는 부분**은 증명되지 않습니다. 그래서
실제 클라이언트로 진짜 세션을 돌렸습니다 — 다이아 5개를 넣고, 철괴 3개를 넣으면서 다이아를
빼고, 닫고, 다시 열어 세어봤습니다. **12/12 통과**, 금고는 줄어든 내용이 아니라 원래대로
돌아왔습니다.

**2. 파일과 파일 사이에도 같은 문제가 있었습니다**

경매가 낙찰되면 물건은 `auctions.yml` 에서 나와 `mail.yml` 로 들어갑니다. **파일이 둘,
기록기가 둘** — 지금까지 사람↔파일에만 적용하던 규칙이 여기도 그대로 필요합니다.
**주는 파일이 먼저** 쓰여야 합니다.

순서는 맞게 적혀 있었습니다. 문제는 **지켜진다는 보장이 없었다**는 것입니다. 각 저장소가
자기 쓰기를 알아서 큐에 넣고 자기 대기열을 계속 돌았기 때문에, 이미 쓰는 중인 저장소가
다른 저장소의 작업이 큐에서 기다리는 동안 **더 새로운 내용을 먼저 내보낼 수 있었습니다.**

추측하지 않고 재봤습니다. 주는 파일 → 받는 파일 순서로 3,000번 돌리면서 **받는 쪽을 먼저,
주는 쪽을 나중에** 읽습니다(둘 다 증가만 하므로, 이 순서에서 "받는 쪽이 앞선다"는 관측은
읽는 타이밍 탓일 수 없습니다):

| | 받는 쪽이 앞섬 | 최대 |
|---|---|---|
| 고치기 전 | **7회 / 3,000라운드** | **649라운드 앞섬** |
| 고친 뒤 | **0회** | — |

649라운드는 좁은 틈이 아닙니다. 두 저장소가 각자 병합하며 **따로 달려나간** 결과입니다.

그래서 저장소가 **자기 쓰기를 큐에 넣지 않습니다.** 틱 펌프가 한 바퀴 분량을 **하나의 작업,
하나의 고정된 순서**로 넘깁니다 — 우편함은 받기만 하므로 언제나 마지막입니다. 저장소마다
있던 대기 슬롯과 루프는 **없어졌습니다**(그 루프가 2.6.5 에서 고쳤던 되감김의 원인이기도
했습니다). 디스크가 느려서 한 바퀴가 아직 안 끝났으면 다음 바퀴는 **만들지 않고 건너뜁니다** —
변경 표시가 남아 있으니 다음 틱에 최신 스냅샷 하나로 합쳐집니다.

**검사**: 서버 내부 **198개**, 봇 28 + 25 + 3 + **12**(금고 세션), 크래시 4 — **270개 전부 통과**.

**제 검사 환경이 틀린 걸 두 번 잡았습니다** (둘 다 플러그인 결함 아님):

1. `pkill -f paper.jar` 가 **자기 자신을 죽이고 있었습니다.** 명령줄에 그 문자열이 들어간
   셸까지 매칭됩니다. 앞선 몇 번의 "원인 모를 중단"이 전부 이것이었습니다
2. `sed` 로 설정을 끄면서 `nameplate: false# 주석` 을 만들었는데, **공백 없는 `#` 은 YAML
   주석이 아닙니다.** 값이 불리언이 아니게 되어 기본값으로 돌아갔고, 켜진 이름표가 이
   클라이언트의 패킷 해석을 깨뜨려 봇이 아무것도 받지 못했습니다. 플러그인이 아니라
   **제 한 줄짜리 편집**이 원인이었습니다

   영업이지 파산이 아니므로 임계치(기본 2,000)를 두었습니다
3. **물가상승률이 하루치로 +94.59% 를 찍었습니다.** 1년이 12일뿐이라 하루 2% 등락이 연율
   27% 가 됩니다. 최소 3일치가 쌓여야 계산하고, 계산한 값도 지수평활하도록 바꿨습니다
4. **금리가 매일 0.5% ↔ 6.5% 로 춤췄습니다.** 산출갭 때문이었습니다 — 작은 서버는 하루
   거래액이 "누가 접속했나"에 따라 0 과 500 을 오갑니다. 최근 3일 평균으로 재고, ±20% 로
   자르고, 평활한 뒤, 준칙의 산출 가중치를 0.5 → 0.25 로, 하루 변동 한도를 3%p → 1%p 로
   낮췄습니다
5. **통화량이 360만에서 꿈쩍도 안 했습니다.** 순위표 서비스를 통해 읽고 있었는데 그쪽은
   몇 초간 캐시합니다. 통화량은 다른 모든 것이 반응하는 숫자라 캐시된 값을 쓰면 안 됩니다 —
   스코어보드 미러를 직접 세도록 바꿨습니다. 이걸 고치고 나서야 물가 반응이 나타났습니다
6. **정기예금이 대출보다 금리가 높아질 수 있었습니다.** 기간 프리미엄이 쌓이면 30일 정기
   15.5% > 대출 12.5% 가 되어, **최대한 빌려서 예금에 넣는 것이 무위험 차익**이 됩니다.
   정기 금리가 "가장 싼 대출 금리 − 0.5%" 를 넘지 못하도록 못을 박았습니다
7. 매도 주문에서 **시장 금고 한도를 세전 금액과 비교**하고 있었습니다. 실제로 나가는 돈은
   세후이므로 한도가 실제보다 빡빡했습니다
8. 시장 화면이 품목마다 인벤토리를 훑어서 **한 화면에 인벤토리 스캔 28번 + 메타 복사 약
   1,000번**이 나왔습니다. 한 번만 훑도록 바꿨습니다

**아직 확인 못 한 것**: 동시 접속자가 여럿인 상태에서의 장기 운영. 봇 한 명으로 만든
거래량은 한 사람분이고, 지니계수·화폐유통속도처럼 **사람이 여럿이어야 의미가 생기는
지표**는 값이 맞게 계산되는 것만 확인했지 실제 분포로 검증하지는 못했습니다.

**검사 중에 찾아서 고친 것** (전부 실제로 재현한 뒤 고쳤습니다):

1. **공모 기업을 공짜로 삼킬 수 있었습니다.** 기초 기업이 자기 주식을 100% 자사주로
   들고 있었는데, 자사주는 인수 때 소각되므로 "살 것이 0주" 가 되어 **현금 257,401골드짜리
   회사가 대금 0원에 합병**됐습니다. 주식을 아무도 안 가진 회사는 주인이 없는 회사입니다.
   이제 발행량의 70%를 **공모 물량**(일반 투자자)이 들고 있고, 인수하려면 그것을 시가 +
   프리미엄에 사야 합니다 — 위 표의 322,000골드가 그 값입니다
2. **주가를 발행주식수로 나누고 있었습니다.** 자사주까지 분모에 넣으면 유통 주식 전부를
   사도 회사 값어치의 일부만 내게 됩니다. 유통 주식(발행 − 자사주)으로 나누도록 바꿨고,
   그 결과 **자사주를 제값에 파는 것이 주당 가치를 바꾸지 않습니다** — 희석이 값어치를
   훔쳐가지 않는다는 뜻입니다
3. **가공 공장이 전부 구조적 적자였습니다.** 원료값 + 유지비가 판매액을 넘었고, 구리
   제련소·유리 공장·네더라이트 공방은 **원료가 제품보다 비쌌습니다**. 실제 시세로 25종의
   수지를 전부 계산해서, 가공품의 수요계수를 올리고(가공은 값어치를 더하는 것이 맞습니다)
   연료 비율을 0.12 로 낮추고, 유지비와 건설비를 **회수 15경제일** 기준으로 다시 잡았습니다
4. **회사가 만든 것을 다 팔지 못했습니다.** 한 주문 상한(2,048개)이 회사의 하루 생산에도
   걸려서, 채석장이 6,000개를 만들면 2,048개만 팔리고 나머지는 창고에 쌓였습니다. 그 상한은
   플레이어가 한 번 클릭해서 창고를 비우지 못하게 하는 것이지 하루치 생산을 막으라는 것이
   아니므로, 회사 주문은 여러 덩어리로 나눠 체결하도록 바꿨습니다
5. **자기가 주문한 건물에 파묻혀 죽었습니다.** `/blueprint build` 는 서 있는 자리에 짓는데,
   거기가 바로 벽이 올라올 자리입니다. 첫 시공 테스트에서 봇이 질식사했습니다. 이제 공사
   구역 안에 있는 사람은 **가장 가까운 벽 밖으로** 밀어냅니다
6. 처음엔 사람을 **위로** 올렸는데, 중력이 다시 떨어뜨리고 다음 틱에 또 올리기를 반복해서
   메시지가 초당 20번 나갔습니다. 옆으로 밀어내는 것이 한 번으로 끝나는 방법입니다
7. **길드 전환 결과가 디스크에 쓰이기 전에 `guilds.yml` 이 먼저 개명됐습니다.** 그 사이에
   서버가 죽으면 길드가 통째로 사라집니다. 이제 변환된 회사를 **쓴 다음에** 개명합니다
8. `corporations.yml` 이 아예 파싱되지 않았습니다 — `copper-smelter:{` 처럼 콜론 뒤 공백을
   빠뜨린 줄이 있었고, YAML 에서 그건 키가 아닙니다

**아직 확인 못 한 것**: 여러 사람이 같은 회사를 두고 경쟁하는 상황(적대적 인수 방어,
주가 조작), 그리고 5만 블록급 대형 청사진의 장시간 시공. 검증은 708블록짜리로 했고
초당 40블록은 그 규모에서 잰 값입니다.

### 2.9.0 — 회사가 망하고, 국가가 끼어들고, 직업이 경제에 붙습니다

**어떻게 확인했나.** 지난 번과 같습니다 — Paper **26.2**(Java 25)에서 기동·`/rpgcore check`·
`/rpgcore reload`·경제일 7일·재시작까지 보고, 살아 있는 플레이어가 필요한 것은 Paper **26.1**
에 봇을 붙여 확인했습니다(`api-version` 만 바꾼 시험용 jar, 코드는 동일).

확인한 것:

| | 결과 |
|---|---|
| 기동 (26.2 / 26.1) | 직업 19 · 업적 50 · 공장 25 · 기업 8 · 예외 0건 |
| 부실 판정 | 자본 −20,200 인 회사가 정산 첫날 **관리종목 공시** (부채비율 "자본잠식") |
| 대표 경고 | 자본이 처음 마이너스가 된 날 "3일 안에 회복하지 못하면 파산" |
| 파산 | 3경제일째 **자본잠식으로 파산** → 자산 청산 → 은행이 **24,514골드 손실 처리** |
| 손실이 은행에 닿는가 | 은행 자본이 마이너스가 되어 **중앙은행이 23,204골드 발권해 메움** (공지됨) |
| 자본 빼먹기 차단 | 빚 120,000 인 회사에서 자본을 넘겨 출금하려 하면 거절, 가능한 금액을 알려 줌 |
| 회사 대출 한도 | 자산 220,000 → 한도 **132,000**(60%), 120,000 대출 후 부채비율 55% 안내 |
| 공급 부족 집계 | 네더라이트 재고 144 → 29(20%) 로 떨어뜨리고 3경제일 유지 |
| 공기업 설립 | 3일째 **"공급이 3일째 부족해 공영네더라이트 공방 설립 (국고 250,000 투입)"** |
| 공기업 지분 | `/stocks buy ST22` → **"공기업이라 지분을 살 수 없습니다"** |
| 민영화 | 재고를 193(134%)로 끌어올리자 **"민영화되었습니다. 10,000주가 거래소에 풀립니다"** |
| 민영화 후 매수 | 100주 1,727골드 → 평가 1,811 (스프레드만큼 차이). 대금은 국고로 |
| 주식 왕복 매매 | DHMC 2,000주 매수 96,436 → 즉시 매도 83,507. **왕복은 손해** |

| `/rpgcore check` | 부실·파산 / 공기업 / 국채 줄이 실제 설정값으로 출력 |

**검사 중에 찾아서 고친 것** (전부 실제로 재현한 뒤 고쳤습니다):

1. **공기업이 영원히 안 생겼습니다.** 부족 판정을 **재고 회복 뒤**에 하고 있었습니다.
   시장은 매 경제일 기준재고 쪽으로 25% 회복하는데, 회복한 재고를 보니 20%까지 바닥난
   품목이 40% 로 보여서 부족이 한 번도 세어지지 않았습니다. 이제 **장 마감 재고**(그날
   장사가 끝났을 때 선반에 남아 있던 양)로 셉니다. 그 값은 저장도 되므로 재시작이
   집계를 흐트러뜨리지 않습니다
2. **공기업을 통째로 살 수 있었습니다.** 지분이 전량 국가 보유라 자사주가 0인데,
   기초 기업은 자사주가 없으면 **신주를 찍어서라도 팔아 주도록** 되어 있었습니다.
   공기업은 매수도 인수도 막았습니다
3. **민영화된 회사를 1,700골드에 통째로 가져갈 수 있었습니다.** 민영화가 국가 지분을
   회사 자사주로 옮겼는데, 그러면 **유통주식이 0** 이 됩니다. 주당 가치는 기업가치 /
   유통주식이므로 정의되지 않고, 하한가 1골드로 떨어집니다. 100주를 104골드에 사면
   그 순간 유통주식이 100주가 되어 그 100주가 회사 전체(1,464,635골드)가 됐습니다.
   이제 민영화는 **지분을 옮기지 않습니다** — 국가 물량 그대로 거래소에 나오고, 판
   대금은 국고로 돌아갑니다. 자사주 매입에도 **유통주식 10% 하한**을 걸었고, 유통이
   0인 회사는 발행주식수로 나누도록 마지막 방어선을 넣었습니다
4. **큰 주문으로 무위험 차익이 났습니다.** 한 주문이 주가를 미는데(발행량의 1%당 12%),
   체결은 **밀기 전 값**으로 했습니다. 1,000주를 주당 18.9에 사면 그 매수가 주가를
   두 배로 밀어서 곧바로 주당 36.2에 되팔 수 있었습니다. 이제 **밀기 전후의 중간값**
   으로 체결합니다(시장이 품목을 한 개씩 훑어 값을 올리는 것과 같은 방식). 밀림폭에
   상한도 넣었습니다 — 큰 매도가 `1 − 밀림` 을 음수로 만들어 **주가가 마이너스**가
   될 수 있었습니다
5. **흑자 회사가 배당을 한 푼도 안 냈습니다.** 주당 배당을 `배당총액 / 유통주식` 의
   **정수 나눗셈**으로 구했는데, 1만 주짜리 회사의 하루 이익 4,867골드로는 주당 배당이
   1골드에 못 미쳐서 `0` 이 되고, 그러면 아무도 못 받습니다. 지분 **비율대로** 나누도록
   바꿨습니다 — 같은 조건에서 20% 주주가 432골드를 받습니다

**아직 확인 못 한 것**: 여러 회사가 동시에 부실해져 은행이 연쇄로 무너지는 상황,
공기업이 8곳 상한까지 차는 장기 운영, 그리고 사람이 여럿 붙은 서버에서의 실업률·지니계수.
전부 1인 봇으로 잰 값이라 분포 지표는 숫자만 맞고 의미는 아직 없습니다.
